这是我学习 Agentic RL 的第一篇记录。起点是 [Search-R1](https://arxiv.org/abs/2503.09516)：它让我第一次比较具体地看到，强化学习如何从“训练模型回答问题”延伸到“训练模型使用工具”。

> 系列路线：Search-R1 → RAGEN → Agent Lightning → rLLM → GRPO/Dr.GRPO → OpenSearch-VL

## 我最初的问题

普通 RAG 的过程通常很固定：

```text
问题 → 检索一次 → 拼接资料 → 生成答案
```

但真实问题往往不是一次检索就能解决的。第一条结果可能只告诉我们一个中间实体，接下来还要根据这个实体继续搜索。于是关键问题变成了：

- 什么时候应该搜索？
- 搜索词应该怎样写？
- 当前证据不够时，要不要继续搜？
- 什么时候停止工具调用并给出答案？

Search-R1 的思路，是不再把这些决定写死在工作流里，而是把它们交给模型策略。

## 搜索也可以是策略的一部分

模型生成的不只是最终答案，而是一条交互轨迹：

```text
思考
→ 生成搜索查询
→ 环境返回检索结果
→ 根据新信息继续思考
→ 再次搜索或回答
```

训练时并不要求存在唯一的“标准搜索轨迹”。只要最后答案正确，就给整条轨迹正向奖励。模型在大量 rollout 中逐渐发现，哪些查询和工具调用顺序更容易走到正确答案。

这让我建立了第一个重要认识：

> Agentic RL 优化的不是某个孤立答案，而是模型在环境中连续做决定的策略。

## 搜索引擎不可微，为什么还能训练

我当时最困惑的一句话是：“搜索操作不可微分并不构成问题。”

搜索引擎确实不是神经网络，无法对网页排序结果直接反向传播。但策略梯度并不要求梯度穿过环境。它只需要知道：

```text
模型生成了哪些动作？
这些动作最终获得了多大回报？
```

在这里，模型生成的搜索查询就是动作，搜索结果是环境反馈，最终答案是否正确则是奖励。训练更新的是“生成该查询的概率”，而不是搜索引擎内部的排序规则。

可以把它类比为下棋：棋盘规则不需要可微，模型仍然可以根据输赢提高某些落子的概率。

## 为什么检索文本要做 mask

一条完整上下文里既有模型自己生成的 token，也有搜索引擎返回的 token。后者不是模型的动作，因此不能拿来计算策略损失。

```text
模型思考 token       → 参与优化
模型搜索查询 token   → 参与优化
搜索返回文本 token   → mask 掉
模型最终回答 token   → 参与优化
```

这个细节很关键：Agent 轨迹里不只有“策略输出”，还混有“环境观测”。如果不区分两者，训练目标就会把模型没有生成的内容也当成动作。

## 我顺便弄懂了平均 EM

Search-R1 的很多实验使用 EM，也就是 Exact Match：模型答案与标准答案完全匹配记为 1，否则记为 0。

平均 EM 就是所有样本正确标记的均值：

```text
平均 EM = 完全匹配的样本数 / 总样本数
```

它简单、客观，但也比较严格。语义正确而表达不同的答案可能被判错。因此读论文结果时，不能只看数值，还要看答案归一化方式和比较基线。

## 这一阶段形成的理解

学完 Search-R1 后，我对 Agentic RL 有了一个最小模型：

```text
策略模型：决定下一步生成什么
环境：执行搜索并返回观察
轨迹：思考、查询、观察和回答的序列
奖励：衡量最终任务是否成功
mask：区分模型动作和环境内容
优化器：提高高回报动作再次出现的概率
```

但这里还有一个没有解决的问题：当环境交互变得更长、奖励更稀疏时，模型真的能稳定学会吗？这把我带到了下一站——RAGEN。
