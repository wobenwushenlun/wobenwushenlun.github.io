上一篇解决了“Agent 能不能通过 RL 学会搜索”。这一篇换个更现实的问题：**它为什么训练着训练着就不学了？**

我结合 [RAGEN](https://arxiv.org/abs/2504.20073) 和它的[官方仓库](https://github.com/mll-lab-nu/RAGEN) 来看。先说结论：Agent RL 的“崩”不一定是 loss 变成 `NaN`，也可能是模型看起来还在输出，实际上只会重复一套安全模板。

## 难点不只是序列变长

普通语言模型 RL 可以把一次回答看成一条序列，而 Agent 的 rollout 更像一个状态机：

```text
状态 s0 → 动作 a0 → 环境反馈 → 状态 s1
状态 s1 → 动作 a1 → 环境反馈 → 状态 s2
...
最终状态 → 任务奖励
```

模型每次输出都会改变后续可见状态。早期动作如果走错，后面的步骤可能全部建立在错误信息之上。因此，多轮 Agent RL 的难点不只是序列更长，而是动作会改变未来的数据分布。

## 最后只给 0 或 1，前面每一步怎么算

假设 Agent 执行十步后才拿到最终的 0 或 1，我们知道整局成功或失败，却不知道：

- 是哪一步搜索真正贡献了成功？
- 哪个动作只是无关绕路？
- 失败是因为早期选错方向，还是最后答案格式不对？

奖励越稀疏、轨迹越长，信用分配越困难。模型很容易放大偶然相关的模式，而不是真正有效的策略。

## Echo Trap：指标还在跑，策略却不动了

RAGEN 给我印象最深的是 Echo Trap。策略可能开始重复环境状态、提示词或曾经获得奖励的表达模板。

表面上看：

- 输出格式更稳定；
- 某些 batch 的 reward 不差；
- 策略熵不断下降。

但实际发生的是：模型找到了一种低风险的“回声行为”，探索空间迅速收缩。它没有学会更好的决策，只是越来越确定地重复已有模式。

这让我意识到，Agent RL 中的训练崩溃不一定表现为 loss 爆炸。更常见的形式是：

> 指标还能运行，策略却失去了有效探索和状态敏感性。

## 我会按这个顺序排查

### 1. Reward 涨了，成功率没涨

可能原因：奖励被格式、长度或某个捷径劫持。

检查动作：抽样查看高奖励轨迹，分别统计任务成功、格式正确和环境推进是否真实发生。

### 2. Policy entropy 掉得太快

可能原因：策略过早确定，进入模板坍缩或 Echo Trap。

检查动作：降低学习率或单轮更新强度，增加有效 rollout 多样性，并检查优势值是否被少量极端样本主导。

### 3. 回答越来越长，但没有更准

可能原因：长度偏置，模型用重复推理堆积 token。

检查动作：同时监控成功率、平均轮数、平均响应长度和单位 token 回报，而不是只看 reward。

### 4. 同一组样本全对或全错

可能原因：组内没有方差，GRPO 无法构造有效相对优势。

检查动作：调整采样温度、每题 rollout 数量或难度分布；对全对、全错组做过滤，但要防止过滤后数据过少。

### 5. KL 或 ratio 突然冒尖

可能原因：旧策略与当前策略差距过大，或者少数 token 的更新幅度失控。

检查动作：核对 rollout 使用的权重版本、clip 范围、batch freshness 和 token mask。

## 监控不能只放一条 reward 曲线

从这一阶段开始，我会把 Agent RL 的监控拆成四组：

```text
任务层：成功率、最终答案正确率
行为层：工具调用次数、状态覆盖、无效动作比例
策略层：entropy、KL、ratio、advantage 分布
数据层：有效样本比例、全对/全错组比例、轨迹长度
```

只有这四层一起看，才能判断模型是在真正学习，还是在利用奖励漏洞。

## 这一篇，我记住了什么

RAGEN 让我不再把 Agentic RL 当成一条漂亮公式。它更像一个会互相影响的动态系统：环境状态变了，采样分布会变；采样变了，奖励和优势也会跟着变；更新太猛，下一轮数据又会完全不同。

接下来的问题是：是否一定要把某个 Agent 框架改造成训练框架？能不能让现有 Agent 原样运行，再从执行轨迹中完成强化学习？这正是 Agent Lightning 要解决的问题。
