> 核对日期：2026-10-25。论文参考 arXiv:2504.19413v1；代码参考 `2c81af3bbe27d9bccb09c772d583df9e9be72ee5`。论文方法、当前 OSS SDK 和托管平台是三个不同对象。本文未运行论文复现或测出新成绩，示例数据与实验方案为教学设计。

## 1. 一句话理解：把历史变成以后能取回的有用信息

用户第一天说“研究报告优先引用原始公告”，一周后开启新会话，Agent 仍应能够按这个偏好工作。简单延长上下文会不断携带大量无关历史；只保存原始对话也没有解决“该找哪一条”的问题。

Mem0 提供记忆基础设施，将交互中的信息提取、持久化并在以后查询时召回。它可以嵌入既有 Agent，不要求把业务逻辑改写成某个完整 Agent 框架。[官方项目](https://github.com/mem0ai/mem0)

这里的“学习”通常发生在外部记忆层，并不意味着模型权重更新。接入长期记忆也不能独自证明 RSI：系统可能只是保留了更多事实，而没有改善产生下一次改进的机制。

## 2. 先分清四种很容易混在一起的内容

| 内容 | 例子 | 主要要求 |
| --- | --- | --- |
| 事实 | 用户所在时区是亚洲某时区 | 来源、身份、时效 |
| 偏好 | 优先引用原始公告 | 适用范围、可修订 |
| 经验 | 抽表前先核对单位和合并口径 | 条件、动作、结果、证据 |
| 任务状态 | 已下载报告，尚未验算 | 检查点、幂等、恢复 |

这张表是本文建议的数据建模区分。不同内容可以存在同一个后端，但不应拥有完全相同的可信度、过期规则和检索策略。

一次性的“这次写得简短一点”未必是永久偏好；“准备更新接口”也不是“接口已经更新”。这类语义区别决定了记忆系统是否会把错误长期放大。

## 3. 2025 论文：提取与更新两个阶段

[Mem0 论文](https://arxiv.org/abs/2504.19413)研究长期多会话记忆，基础架构先从交互和上下文抽取候选事实，再与已有相关记忆比较，选择写入操作；另外提出图记忆变体 Mem0g。

论文方法可以概括为：

```text
当前交互 + 历史摘要 + 最近消息
  → 抽取候选事实
  → 找到相关旧记忆
  → 判断新增 / 更新 / 删除 / 不操作
  → 更新存储

后续问题 → 检索相关记忆 → 与当前上下文共同回答
```

这是理解原论文的概念图，不应直接当成当前版本的逐函数调用图。

### 3.1 四种操作的教学例子

| 操作 | 输入与旧记忆的关系 | 自拟示例 |
| --- | --- | --- |
| ADD | 新事实 | 之前没记录默认输出语言 |
| UPDATE | 补充或修订已有信息 | 把模糊偏好补充为更具体条件 |
| DELETE | 旧信息不再适用 | 已明确撤销某个偏好 |
| NOOP | 重复或无关 | 再次确认同一条事实 |

从系统角度，原地更新能减少重复和查询冲突，却会把“是否覆盖旧信息”的判断放在写入时。若判断错误，历史证据可能被破坏，因此实际系统还需要审计或版本历史。

## 4. 当前版本：不要把旧论文算法当成现在的 add

当前项目 README 和代码显示，主要记忆写入流程转为追加式事实抽取；开源 `_add_to_vector_store` 使用 additive extraction 路径。不能再概括成“每次 add 必然让 LLM 在四操作中决策”。[固定源码](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/memory/main.py)、[当前写入文档](https://docs.mem0.ai/core-concepts/memory-operations/add)

**追加式自动写入，不等于整个系统没有显式 update/delete 管理接口。** 要分别检查数据入口、管理 API、索引维护和身份元数据保护。

### 4.1 两种路线的取舍

| 设计 | 写入阶段 | 查询阶段 | 主要风险 |
| --- | --- | --- | --- |
| 抽取 + 合并更新 | 处理重复与冲突 | 读取较紧凑状态 | 错误覆盖、写入推理成本 |
| 追加 + 检索消歧 | 保留更多历史事实 | 识别时间与有效状态 | 历史累积、旧事实误用 |

这不是谁永远优于谁的问题。比如“我三月在北京、五月搬到上海”既有当前状态也有历史价值；把旧记录简单删除，会影响回答三月行程的问题；把两条都返回而不提供时间，又会造成当前地址冲突。

### 4.2 要检查实际执行路径

源码中可能出现滞后的 docstring。阅读时优先追踪调用链、使用的抽取 prompt、实际落库与返回结果，再与说明对照，避免只搜到 UPDATE 字符串就断言当前自动写入仍是旧算法。

## 5. 写入链路：从消息到可查询记忆

根据当前代码组织，可带着以下问题检查过程：

```text
输入消息与身份范围
  → 规范化与校验
  → LLM 提取事实，或 infer=False 的直接存储路径
  → embedding / 去重 / 存储
  → 历史记录和实体关联
  → 返回实际写入结果
```

这幅图是职责概括，具体操作顺序以固定版本源码为准。批量写入、单条回退、实体关联失败等边界也应检查，不要把一次 SDK 返回等同于所有派生数据绝对完整。

### 5.1 infer=False 不代表“自动提取但更省钱”

当前文档区分提取事实与直接保存消息。关闭推断时，应用需要自己决定输入是否已适合长期保存。[写入语义](https://docs.mem0.ai/core-concepts/memory-operations/add)

### 5.2 写入时应保存什么来源

下面是建议的应用层 provenance，而非 Mem0 保证自带的完整字段：

```json
{
  "source_type": "user_statement",
  "source_message_id": "msg-018",
  "source_trace_id": "trace-004",
  "observed_at": "2026-10-25",
  "valid_from": "2026-10-25",
  "confidence_kind": "explicit",
  "scope": "report-writing"
}
```

模型抽取的 confidence 不是客观概率。显式陈述、模型推断、工具验证应有不同标记。来源缺失时，后续很难解释系统为什么如此确信一条错误记忆。

## 6. 检索：相关不等于正确，更不等于当前有效

当前 OSS 实现包含语义检索与可选关键词、实体信号；配置与后端会影响实际能力。文档提供 `explain=True` 来检查检索分数组成。[Search 文档](https://docs.mem0.ai/core-concepts/memory-operations/search)

下面是我用于理解检索的通用分解，并非 Mem0 的精确评分公式：

```text
候选来源：语义相似 + 关键词匹配 + 实体关联
约束范围：用户 / Agent / session / 业务元数据
结果选择：阈值、排序、重排、去重、上下文预算
应用消歧：时间、来源、冲突、任务适用性
```

不能因为最终 score 高，就认为内容可信。它可能只表示“与问题很像”。例如旧地址会与“现在住哪里”高度相似，但时间语义不一定正确。

### 6.1 阈值不是通用常数

换 embedding、索引、融合公式或任务，分数分布会变。需要用带标签的查询集合观察召回与误召回，而不是照抄一个社区阈值。

### 6.2 Top-k 与上下文预算不是同一件事

返回 5 条很长记忆，可能比 20 条短事实更贵。最好在应用层依据 token、覆盖率和冲突关系再次选择，不只按条数控制。

## 7. 身份与权限：filters 不是完整授权系统

当前 Python API 将查询的 `user_id`、`agent_id`、`run_id` 放在 filters 中；`add` 接口仍接受相应顶层参数。版本差异会导致旧教程调用报错。[接口文档](https://docs.mem0.ai/core-concepts/memory-operations/search)

但任何客户端都能传 `user_id="alice"`，不代表这个客户端有权访问 Alice。服务端应从已认证身份构造或校验范围。过滤表达式约束查询，认证授权决定谁能选择这个范围。

还要避免把全部记忆限定到每次都变化的 `run_id`，导致新会话无法读取旧偏好。相反，若所有用户共享同一 scope，又会产生身份串扰。

## 8. 最小 API 示例

以下按固定版本的 OSS Python 调用形式编写，需要有效的 LLM、embedding 与后端配置。本文未发起真实 API 调用，不把示例当作实测。[源码入口](https://github.com/mem0ai/mem0/blob/2c81af3bbe27d9bccb09c772d583df9e9be72ee5/mem0/memory/main.py)

```python
from mem0 import Memory

memory = Memory()

memory.add(
    [
        {"role": "user", "content": "技术笔记优先使用中文解释，并保留原始来源。"},
        {"role": "assistant", "content": "已记录这次写作要求。"},
    ],
    user_id="study-user",
    metadata={"topic": "technical-writing"},
)

found = memory.search(
    query="这位用户对技术笔记有什么要求？",
    filters={"user_id": "study-user"},
    top_k=5,
    explain=True,
)

for item in found.get("results", []):
    print(item["memory"])
```

真实应用中应检查：空结果、抽取错误、后端可用性、返回 schema、部分写入和日志中的敏感内容。不要因为 add 没抛异常就假定目标事实已经被正确抽取。

## 9. 图记忆：实体关联不等于任意多跳推理

原论文的 Mem0g 用实体与关系扩展基础记忆，目的是表达跨事实联系。当前项目中的实体链接、图后端和托管能力需要分别核对，不能因为出现“entity”一词就视为原论文完整图算法。

教学例子：

```text
项目 A → 使用 → 库 B
库 B → 最新兼容版本 → v2
项目 A → 当前固定版本 → v1
```

这些关系帮助定位，但回答“项目现在是否能直接升级”仍需检查依赖约束与测试。关系图保存的是信息结构，不替代验证与程序执行。

## 10. 怎样解读论文和官网数字

2025 论文在 LoCoMo 上比较记忆系统、RAG、全上下文等方案；摘要报告的相对提升与 token、延迟收益有具体比较基线，不能改写成“所有任务提高 26 个百分点”。[论文与实验设置](https://arxiv.org/html/2504.19413v1)

当前 README 另外明确说明，展示的部分新算法成绩来自包含专有优化的托管平台，不能保证 OSS SDK 达到完全相同的数字。[版本与成绩边界](https://github.com/mem0ai/mem0/tree/2c81af3bbe27d9bccb09c772d583df9e9be72ee5)

读到任意分数，我会先填下面这张表：

| 要素 | 要核对的内容 |
| --- | --- |
| 实现 | 原论文、开源 SDK、自托管服务还是云平台 |
| 数据 | 完整集、子集、具体任务类型与切分 |
| 模型 | 抽取、embedding、生成、judge 是否相同 |
| 成本 | 写入成本、查询成本、回答成本是否都算 |
| 延迟 | 平均、p50、p95，冷启动还是热启动 |
| 预算 | 返回多少候选，给模型多少 token |
| 统计 | 重复次数、波动、失败样本处理 |

特别注意，LoCoMo 类长期对话问答能力与开放环境工具执行能力不同。前者进步不能自动证明 Agent 更会规划和恢复。

## 11. 一个比“记住了名字”更有价值的实验

创建一组教学多会话数据，覆盖：稳定偏好、一次性要求、时间变化、撤销要求、同名实体、错误推断、不同用户，以及带指令的外部材料。

例如：

```text
会话 1：默认输出中文。
会话 2：这次交给海外同事，请用英文。
会话 3：恢复通常习惯，写一份普通技术解释。
问题：第三次应默认使用什么语言？依据是哪条记录？
```

这能检测系统是否把一次性要求误当长期偏好。

### 11.1 对照组

| 组别 | 记忆策略 |
| --- | --- |
| A | 无长期记忆，只看当前会话 |
| B | 全部历史直接输入，记录上下文上限 |
| C | 普通切块检索 |
| D | Mem0 记忆检索 |
| E | D 加应用层来源与时间消歧 |

固定生成模型与答案预算，分别测回答准确率、事实召回、记忆污染、身份泄漏、旧事实误用、写入费用和查询延迟。

### 11.2 如何避免测试泄漏

按时间顺序写入，只允许当前时点之前的材料。测试答案和最终评分理由不能成为记忆输入。比较时为每组独立创建快照，不能让后一组继承前一组学到的答案。

## 12. 成本模型与维护债务

下面是用于预算的教学公式：

```text
总成本 = 写入抽取 + embedding + 存储维护
       + 查询检索 + 可选重排 + 答案生成
       + 错误记忆导致的纠正与重试
```

追加写入把一部分冲突处理移到查询时，也可能导致存储与检索候选增长。原地合并减少体积，却需要更谨慎地保留历史。不能只看一次 query 的 token，忽略记忆持续几个月后的维护成本。

对自进化系统，错误经验的成本尤其高：一次错误可能被多次检索，在后续任务中被反复强化。因此记忆最好支持证据、适用条件、回滚与失效，而不只有一句自然语言总结。

## 13. 源码阅读路线

固定快照：[Mem0 source](https://github.com/mem0ai/mem0/tree/2c81af3bbe27d9bccb09c772d583df9e9be72ee5)。

| 阅读对象 | 关注问题 |
| --- | --- |
| `mem0/memory/main.py` 的 `add` | 身份校验、推断开关、实际写入路径 |
| `_add_to_vector_store` | additive 抽取、去重、批量写入与返回 |
| `search` 与检索辅助函数 | filters、混合信号、explain、重排 |
| 实体关联相关函数 | 实体与记忆如何连接，失败怎样处理 |
| 显式 update/delete | 删除与更新怎样影响索引和历史 |

先阅读同步链路，再对照异步实现；不要假定二者在异常、批处理和超时方面天然完全相同。

## 14. 一天 5 小时练习

| 时间 | 动作 | 验收 |
| --- | --- | --- |
| 60 分钟 | 对照论文和当前 add 代码 | 一张版本差异表 |
| 75 分钟 | 写入多会话合成数据 | 可检查的事实与来源 |
| 60 分钟 | 检索并查看 explain | 召回与分数分解 |
| 60 分钟 | 注入身份、时间与撤销案例 | 失败分类与最小复现 |
| 30 分钟 | 统计在线和摊销成本 | 分项成本表 |
| 15 分钟 | 闭卷复述 | 为何长期记忆不等于 RSI |

## 15. 自测、速查与资料

先回答五题：

1. 自动追加与显式删除 API 为什么不矛盾？
2. 为什么相似度最高的记忆仍可能是错的？
3. filters 与授权有什么区别？
4. 怎样区分一次性语言要求与长期偏好？
5. 论文相对提升 26% 为什么不是提升 26 个百分点？

<details>
<summary>参考要点</summary>
<p>写入算法和管理接口属于不同路径；相似度不包含真值与有效时间保证；filters 限定查询范围，授权验证调用者能否使用该范围；保存上下文与时效并构造后续恢复场景；相对提升以基线为分母，而百分点是绝对比例差。</p>
</details>

速查：先定身份，再定来源和时间；先查版本，再用 API；先测写入正确性，再测召回；计入维护成本；不要把云平台成绩当作本地复现。
