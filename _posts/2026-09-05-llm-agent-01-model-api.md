这套课程的目标不是熟记 Claude Code 命令，而是借助它学习如何设计、实现和评测 LLM Agent。Claude Code 是你的编程与学习助手；你写的 Python 程序才是接下来要研究的 Agent。

第一章只解决一个问题：**一次模型调用究竟发生了什么，程序应该观察哪些信息？**

建议用时 3 小时：概念 45 分钟、代码 45 分钟、实验 60 分钟、自测 30 分钟。今天可以先读三章，动手练习另排时间；前三章完整练习合计约 10 小时，不要求一天全部掌握。

系列导航：**第 1 章** → [第 2 章：Agent 控制循环](/notes/llm-agent-02-control-loop/) → [第 3 章：工具调用](/notes/llm-agent-03-tool-calling/)。

## 1.1 先分清三个对象

| 对象 | 本课中的职责 | 不应混淆的地方 |
| --- | --- | --- |
| LLM | 根据输入上下文生成输出 | 模型输出一段代码，不代表已经运行代码 |
| Python 应用 | 保存消息、发送请求、处理响应 | 应用负责控制执行和资源，不是一个被动显示器 |
| Claude Code | 帮助你理解、编写和检查程序 | 它的内部运行过程不等于你自己的实验程序 |

例如你问：“这个函数为什么算错了？”模型只在收到函数文本后，才能基于文本分析。模型说“我会检查测试”，也不代表测试真的执行了。是否执行、在哪里执行、权限是什么，必须从应用与工具的实际记录判断。

课程前三章不训练模型权重。我们保持模型基本不变，研究输入组织、行动接口和执行循环。这样做改变的是模型周围的系统，而不是做一次 SFT 或强化学习训练。

本章也不把某个产品的表现当成其内部算法的证据。观察到它先搜索再回答，只能说明这次可见轨迹如此，不能据此断言它实现了某篇论文的全部算法。

## 1.2 LLM：条件生成，而不是查询确定答案

可以用下面的概念式描述文本生成：

```text
p(输出序列 | 输入上下文)
  = 每一步 p(下一个 token | 输入上下文, 已生成 token) 的乘积
```

你不需要现在推导 Transformer，但需要理解两个后果。

第一，模型不是一个给同样参数就保证返回相同结果的普通业务函数。模型服务、采样、数值实现等因素会影响结果；做实验不能凭一次成功下结论。

第二，生成内容可能合理但不正确。对代码任务，答案是否正确要靠编译、测试、规格和代码检查等外部证据，而不是答案语气有多肯定。

“生成下一个 token”不意味着模型只能完成简单任务；复杂能力可以体现在整个输出与交互过程中。但我们也不需要把语言流畅性解释成可靠验证能力。

## 1.3 消息不是一根无限长的字符串

本课采用 Anthropic Messages API。对应用来说，一次请求可以拆成：

```text
model       选择具体模型
system      从开始就适用的行为说明
messages    本次提供给模型的对话历史
max_tokens  本次允许生成的输出上限
```

示意请求：

```python
request = {
    "model": model_id,
    "max_tokens": 512,
    "system": "用中文解释代码。缺少信息时说明缺口。",
    "messages": [
        {"role": "user", "content": "这段函数为什么返回 20 而不是 80？"}
    ],
}
```

这里的 `model_id` 是你有权限使用的实际模型 ID，不能把占位名称直接提交给服务。

普通 Messages 多轮调用由客户端维护所需历史，并在下一次请求发送。它不会仅凭你上一次请求过，就自动知道当前问题中的“它”指什么。[官方 Messages 文档](https://platform.claude.com/docs/en/build-with-claude/working-with-messages)

例如第二轮应显式包含必要历史：

```python
messages = [
    {"role": "user", "content": "项目规定 discount=0.2 代表八折。"},
    {"role": "assistant", "content": "明白，最终价格应为原价的 80%。"},
    {"role": "user", "content": "那么原价 100，最终价格是多少？"},
]
```

历史不是越多越好。包含错误约定、过时文档或无关日志的历史，可能增加干扰。第 6 章会专门研究上下文选择；本章先确保你知道自己发了什么。

## 1.4 Token、上下文与成本分别限制什么

Token 是模型处理的编码单元，不等于字符、汉字或单词。不要用“一个汉字固定等于一个 token”估算所有输入。

| 概念 | 你需要记住的含义 |
| --- | --- |
| 输入 Token | 模型处理本次请求中的提示、历史等内容所涉及的量 |
| 输出 Token | 本次生成所涉及的量；具体字段含义以模型文档为准 |
| 上下文窗口 | 模型能够处理的上下文容量，不等于输出长度 |
| `max_tokens` | 本次输出上限，不是整个 Agent 的总预算 |
| 总调用预算 | 由应用额外设置的轮数、工具次数、时间或费用限制 |

在无缓存、纯文本、没有额外工具费用的简化情况下：

```text
总模型费用 ≈ Σ轮次(本轮输入 Token × 输入单价
                  + 本轮输出 Token × 输出单价)
```

若每轮都重新发送增长的历史，后面的输入会更大。缓存、特殊 Token 计量和服务端工具可能改变实际账单，因此本课记录服务返回的 `usage`，不在代码里写死价格。

采样参数也是模型相关的。温度可以作为理解随机性的概念，但不保证当前所选模型支持手动设置；本课请求不传 `temperature/top_p/top_k`，避免把旧教程参数当成普遍接口。具体支持情况查看所选模型的官方说明。

## 1.5 响应里最重要的不只有文本

示意响应如下，数值不是实测用量：

```json
{
  "content": [{"type": "text", "text": "模型选择动作，程序执行动作。"}],
  "stop_reason": "end_turn",
  "usage": {"input_tokens": 20, "output_tokens": 14}
}
```

`content` 是内容块数组。第 3 章会加入 `tool_use`，因此不要假定 `content[0]` 永远是最终答案。

本课程先处理这些状态：

| 状态 | 应用如何理解 | 本课策略 |
| --- | --- | --- |
| `end_turn` | 本轮生成正常结束 | 提取文本，但不标记“任务已验证成功” |
| `max_tokens` | 达到本次输出上限 | 标记截断，检查后再决定是否重试 |
| `tool_use` | 需要客户端执行工具 | 第 3 章才接入执行分支 |
| 其他状态 | 可能属于拒绝、暂停或其他协议状态 | 显式停止并检查，不能全部当成成功 |

最容易踩的坑是：截断的 JSON 恰好前半部分看起来合理，就拿去执行后续操作。本课不会执行模型生成的代码，也不会把非正常结束的结果自动当成完整答案。

## 1.7 阅读核心代码

完整文件提供普通与流式两条路径。先理解普通路径：

```python
with Anthropic(timeout=30.0, max_retries=2) as client:
    response = client.messages.create(**request).model_dump(mode="json")
```

这是传输与模型响应层，尚未包含 Agent Loop。重试交给 SDK，没有再套一层无限重试。

流式路径：

```python
with client.messages.stream(**request) as stream:
    for piece in stream.text_stream:
        print(piece, end="", flush=True)
    response = stream.get_final_message().model_dump(mode="json")
```

流式输出让你更早看到内容，不表示产生了多次独立回答。最终仍需获得完整消息，检查停止原因与用量。[Anthropic Python SDK](https://github.com/anthropics/anthropic-sdk-python)

一个容易忽视的边界：流中断时，终端可能已经显示一半文本；这不等于拿到了完整响应。本示例会暴露异常，不自动把部分内容写回下一轮历史。

## 1.8 三个小实验

### 实验 A：信息缺失会怎样

目标：理解回答依赖上下文，而不是只依赖模型名。

修改请求，比较“直接问 discount=0.2 的价格”和“先给八折定义再问价格”。记录答案、是否提出澄清、输入用量。再使用“discount=0.2 代表只支付 20%”的新约定，观察是否随明确规格改变。

不要把某一次表现推广成所有任务规律。你要提交的是三组输入和输出，以及它们为何不同的解释。

### 实验 B：输出预算不足

目标：区分结束与截断。

在所选模型允许的参数范围内，把 `--max-tokens` 调低，并让请求生成比上限明显更长的内容。记录实际 `stop_reason`。若请求直接因参数限制被拒绝，也把它记为接口实验结果，而不是模型推理失败。

### 实验 C：普通输出与流式输出

目标：理解显示方式与任务正确性是两回事。

分别运行普通 `--live` 和 `--live --stream`。记录“第一段文字何时出现”和“整次请求何时完成”。预期差别是交互体验，不保证流式总耗时更短，更不保证答案更好。

没有 API 权限时，先修改离线响应的 `stop_reason` 为 `max_tokens`，检查提示是否变化。用离线分支测试程序，用真实分支研究模型，二者分开记录。

## 1.9 常见错误与修复方向

- **401/403**：先核对认证和权限，不要反复改 Prompt。
- **模型不存在或无权限**：核对模型 ID 与服务账户，而不是盲抄旧教程。
- **400 参数错误**：阅读错误及所选模型接口，不要无限重试。
- **429、临时网络错误**：适度退避；限制重试次数，注意重试可能增加时间与费用。
- **超时**：SDK 的超时与重试配置不等同于整个任务的绝对截止时间。
- **JSON 看似规范但字段不对**：“请输出 JSON”不是验证机制；解析、类型验证和任务语义验证是不同层。

SDK 能支持的传输重试不能代替工具幂等设计；这一章没有会写文件或付款的工具，第 3 章以后再分开讨论副作用。

## 1.10 自测与通关

先合上正文回答，暂时不要看答案。

1. Claude Code、模型 API、你自己的 Agent 程序有什么区别？
2. 为什么第二轮只发送“那它呢”可能不够？
3. `max_tokens=512` 为什么不能限制整个任务总消耗？
4. `end_turn` 能否证明代码修复成功？
5. 流式输出显示完一段文字，为什么仍要等最终消息？

<details>
<summary>完成自测后查看参考要点</summary>

<p>1. 分别是现成应用、模型调用接口和你实现的控制系统。2. 普通 Messages 请求需要客户端提供必要历史。3. 它是单次输出上限，输入、多轮和重试另计。4. 不能，它是生成状态而非测试结果。5. 仍需判断响应是否完整，以及停止原因、完整内容和用量。</p>

通关产物：一个能运行的客户端、一份至少三行的实验记录，以及你不用查资料也能讲清的一次请求生命周期。不以“读完”为通关条件。
