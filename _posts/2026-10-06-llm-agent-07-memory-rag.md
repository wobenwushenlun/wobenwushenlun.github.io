第 6 章讨论了“本轮应该把哪些证据放进上下文”。这章把时间拉长：**本次任务结束后，哪些信息值得留下？下一次该相信多少，又该在什么时候忘掉？**

我们继续使用折扣项目。今天的产物是一个能关闭后重新打开的 SQLite 记忆库，并实现读取前的有效性检查。它可以成为 RAG 的检索前端，但不会仅因为存进了数据库就自动具备生成能力。

建议用时 4 小时：概念与资料 45 分钟、实现 65 分钟、污染与失效实验 85 分钟、迁移和复述 45 分钟。

## 7.1 记忆到底存在哪里

如果你把上一次结论写入文件，再在下一次请求中读回来，模型参数并没有更新。变化的是外部存储和本次输入。

本课程采用以下工作分类。它帮助分配职责，不要求所有 Agent 框架都使用相同名称。

| 类型 | 保存什么 | 折扣项目中的例子 | 主要风险 |
| --- | --- | --- | --- |
| 工作记忆 | 当前任务的状态与近期观察 | 已读 README，还没检查调用方 | 摘要漏掉约束 |
| 情景记忆 | 某次任务发生了什么 | 某版本把折扣额误当成应付额 | 具体案例被过度推广 |
| 语义记忆 | 有适用范围的知识或约定 | 该项目的 discount 表示减去比例 | 业务约定过期 |
| 程序性记忆 | 可复用的操作步骤 | 先核对折扣定义，再检查边界测试 | 把局部经验写成硬规则 |

长期记忆也不是“所有聊天永久保存”。全量记录更适合做审计原始材料；用于检索的记忆通常需要提炼、去重、版本化和失效管理。

关键区别是：**记录过一次，不等于验证过一次；验证过一次，不等于永远适用。**

## 7.2 RAG 与 Agent 记忆是什么关系

RAG 原论文把参数化模型与可检索的外部信息结合，用检索到的材料支持生成，并研究了具体训练与生成方案。今天工程中常说的 RAG 通常泛指“先检索、再基于材料生成”的一类系统，不能把所有实现都当成原论文复现。[RAG 原论文](https://arxiv.org/abs/2005.11401)

在我们的项目中，关系可以写成：

```text
资料或历史经验
    → 提取、校验与保存
    → 按任务查询候选
    → 检查作用域、版本、有效期与冲突
    → 第 6 章的上下文组装
    → 模型基于材料生成
    → 通过原始证据与外部标准检查答案
```

知识库可以只包含项目文档，不含任何历史任务；这也是检索增强。记忆库也可以只支持策略选择，不直接生成回答。二者相关，但不是同一个概念。

本章代码止于“检索出可用记录并组装证据”。接入模型生成的步骤留作迁移练习，输出会明确标注 `offline_retrieval_only`。

## 7.3 为什么不马上上向量数据库

向量检索解决“语义相近内容如何召回”的问题，但它不能替你决定谁有权限看这条记录、记录是否过期、两个结论是否矛盾。

本课先用 SQLite 和词法重叠建立可解释基线。沿用第 6 章的英文词与代码标识符分词规则，不引入 Embedding 服务或第三方存储。

三种检索信号各有用途：

- 文件名、函数名、错误代码：精确或词法匹配往往是必要基线。
- 自然语言的改写、同义表达：语义召回可能有帮助。
- 业务范围、时间、来源版本：应作为元数据过滤条件，不能只交给相似度评分。

后续可以先扩大候选集合，再用重排器区分相关性；但相关性与可信度仍是两条轴。与问题高度相关的错误结论尤其容易污染答案。

## 7.4 设计一条能被追责的记忆

示例定义：

```python
@dataclass(frozen=True)
class Memory:
    id: str
    scope: str
    key: str
    kind: str
    text: str
    source: str
    revision: str
    expires_at: int
    verified: bool = False
```

不要只盯着 `text`。其余字段决定它能否被使用：

| 字段 | 意义 | 本课例子 |
| --- | --- | --- |
| scope | 属于哪个项目或知识范围 | discount-demo |
| key | 讨论同一事实的归组键 | discount.meaning |
| source / revision | 来源及其文本版本 | README.md / SHA-256 |
| expires_at | 到期边界 | 逻辑时间 200 |
| verified | 是否已由宿主流程确认 | 人工核对后写入 true |

`verified` 不是模型可以通过一句“我很确信”自封的权限。示例在受控种子数据里由程序指定它；真实系统需要规定谁能确认、凭什么确认、验证结果保存在哪里。

本例每条记录只有一个来源。复杂结论常需要多个文件共同支持，应把 `source/revision` 扩展为证据清单，而不是拿 README 的哈希代表整个仓库。

## 7.5 写入策略比读取技巧更早决定质量

可以把写入过程看成四步：

```text
原始轨迹 → 候选经验 → 核对证据及适用范围 → 保存记录
```

对这个项目，一条合格候选是：“在 README 的某个版本中，discount 表示减去比例。”一条危险候选是：“所有项目的 discount 都应使用 1-discount。”

语义相近的记录不一定重复。例如“折扣比例为 0.2”和“最终应付比例为 0.8”支持同一个算例，但字段含义不同。我们的简单实现只对相同 `key` 与相同文本去重，不声称能识别语义等价。

同一事实键的不同文本会被保守地视为候选冲突。真实应用中它们可能只是措辞不同，需要进一步核对；默认静默选择相似度最高的一条，会把冲突藏起来。

程序还使用参数化 SQL，避免把记忆文本拼成查询语句。但 SQL 注入防护不能处理 Prompt Injection；数据库里的自然语言回到模型后，仍要被当作外部数据。

## 7.6 检索的执行顺序

代码：[ch07_memory.py](/assets/learning/llm-agent/ch07_memory.py)。依赖原有 `ch03_tools.py`、`ch06_context.py` 和教学 `fixtures`，保持它们在同一目录即可。

检索顺序是：

```text
只查询当前 scope 且 active 的记录
  → 排除未验证记录
  → 排除到期记录
  → 排除来源版本已变化或无法确认的记录
  → 找到与查询相关的事实键
  → 检查这些键是否存在互相不同的候选结论
  → 词法排序、去重、top-k 与字符预算
```

为什么先过滤项目再排序？因为跨项目的错误约定可能比本项目的正确记录更像当前问题。即便最后不放入上下文，也不该在诊断日志里输出别的项目的记录内容。

示例的 `scope` 是宿主提供的分区键，不是生产级认证授权系统。用户若能任意传入别人的 scope，仍可能越权；真实应用必须从身份与访问策略推导允许范围。

返回值同时包含 `selected`、`excluded`、`conflicts` 与 `context`。这些记录使你能区分没有召回、被有效性检查拒绝和被预算裁掉。

## 7.7 先跑持久化与失效实验

```powershell
python -B assets/learning/llm-agent/ch07_memory.py
```

程序在系统临时目录创建 SQLite 数据库，写入四条教学记录，关闭连接，再重新打开后检索。结束时只清理它自己的临时目录，不会把数据库留在博客的公开资源路径。

种子数据包含：本项目的有效事实、未验证猜测、旧版本记录、另一个项目的相反约定。默认应仅选中 ID 为 `fact` 的有效事实。

逻辑时间固定为 100，过期边界为 200，便于重复测试；不是用电脑日期控制演示。可以执行：

```powershell
python -B assets/learning/llm-agent/ch07_memory.py --scenario expired
python -B assets/learning/llm-agent/ch07_memory.py --scenario stale
python -B assets/learning/llm-agent/ch07_memory.py --scenario forgotten
```

到期时，`expires_at <= now` 的记录不可用；版本变化时，旧事实需要重新查证；`forgotten` 会将有效记录标为 inactive，保留审计行。

这里的遗忘是“不再供检索使用”，不是隐私删除保证。若需要彻底擦除敏感数据，还要处理数据库文件、备份、日志与其他副本，本示例不提供那种能力。

## 7.8 冲突不是用多数票掩盖

```powershell
python -B assets/learning/llm-agent/ch07_memory.py --scenario conflict
```

程序故意加入一条同范围、同来源版本、同事实键但结论相反的“已验证”记录。此时输出应为 `needs_resolution`，冲突键对应记录都不进入选中上下文。

这模拟了验证流程可能犯错：`verified=true` 也需要冲突检测，不能被视为无条件真理。

合理的解决方法是重新读原始规格、确定适用版本与业务条件，再显式停用错误记录或写入新记录。重复存三次旧结论不能让它比一次正确证据更可信。

示例允许返回其他不冲突的记录，但整体状态会保留 `needs_resolution`。生成端必须看到这个状态，不能只拿 `context` 后假装信息完整。

## 7.9 怎样把检索接回生成

迁移到真实模型时可以采用以下接口草图，注意它不是可直接运行的完整 API 程序：

```text
result = store.retrieve(宿主确定的项目, 查询, 当前来源版本, 当前时间)
若 result.status == needs_resolution：返回冲突与待核验项
若 result.status == empty：读取当前项目原始文件，或说明未知
否则：将 result.context 作为不可信证据交给 ContextBuilder
模型生成：结论 + 引用记录 ID + 来源 + 不确定项
验证：回到来源检查引用是否真的支持结论
```

如果作为工具返回，应遵守第 3 章的 `tool_result` 协议，而不是把数据库文本拼进系统提示。数据库可持久化，并不意味着其中的话有更高指令优先级。

读取旧经验的价值往往是提示“去哪里查、需要检查什么”，不一定是直接提供答案。例如记忆提示注意折扣语义，可以帮助调查；当前代码已经修复后，旧失败轨迹不能证明新版本仍然有 Bug。

## 7.10 对照实验与评价

准备三个设置：无记忆、只读取通过过滤的记忆、读入全部历史。第三组用于暴露污染，不是推荐部署方式。

先在离线阶段评价机制：跨项目泄漏是否为零、到期记录是否被排除、同一事实冲突是否显式暴露。再接入模型后评价任务结果：查证步骤是否减少、答案是否引用正确、失败率与总用量是否变化。

| 观察 | 可能的解释 | 下一步验证 |
| --- | --- | --- |
| 读了记忆后答得更快 | 少做了检索，也可能跳过了必要查证 | 看引用、版本与工具轨迹 |
| 召回很多记录 | 命中率高，也可能包含大量无关经验 | 人工标注必要记忆与噪声 |
| 无记忆与有记忆效果相同 | 任务太简单，或记忆没被真正使用 | 设计需要历史约束的新任务 |
| 有记忆反而错误 | 过期、冲突、范围或摘要问题 | 逐项移除记忆并重跑 |

离线脚本没有模型调用，不生成这些性能结论。它只证明数据库重开和过滤逻辑按设计工作。

## 7.11 迁移作业、自测与资料

迁移作业：支持多来源证据清单。只要其中一个必要来源变化，就把记忆标为需要重新验证。再增加一个“只影响某个版本范围”的业务规则，用两套项目数据验证不会混用。
