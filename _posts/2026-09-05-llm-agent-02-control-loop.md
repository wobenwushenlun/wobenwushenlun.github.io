第一章完成了模型调用，但“反复调用模型”本身不是一个完整设计。这一章要回答：**谁决定下一步做什么，执行结果放在哪里，什么时候必须停止？**

建议用时 3 小时。完成后，你应能不依赖框架写出一个有状态、可追踪、不会无限循环的运行器。

系列导航：[第 1 章：模型与 API](/notes/llm-agent-01-model-api/) → **第 2 章** → [第 3 章：工具调用](/notes/llm-agent-03-tool-calling/)。

## 2.1 Agent 的重点是控制权

先看两个处理代码问题的程序。

程序 A 的执行顺序事先写死：

```text
读 README → 读指定文件 → 生成解释 → 返回
```

程序 B 则让模型结合当前证据选择下一步：

```text
观察当前任务与证据
  → 决定读测试、搜索代码、继续调查或结束
  → 程序执行允许的动作
  → 把结果反馈给模型
  → 再决定下一步
```

Anthropic 的工程文章把前者这类预定义路径称为 Workflow，把模型动态决定过程和工具使用的系统称为 Agent。这是有用的工作定义，不是所有研究文献唯一认可的分类。[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)

固定工作流也可以包含模型调用；Agent 也可以含有确定性规则。真实系统往往混合两者。关键问题是：在什么位置，把哪些决定交给了模型？

如果任务永远是“读取固定配置并总结”，确定性工作流可能已经足够。这里先学习更通用的运行器，是为了理解控制机制，而不是认定自主性越高越好。

## 2.2 六个概念构成最小模型

假设用户提出：“折扣函数的测试为什么失败？先解释，不要修改文件。”

| 概念 | 这个任务中的实例 | 谁持有或产生 |
| --- | --- | --- |
| 目标 `goal` | 找到测试失败原因，给出证据 | 用户提供，程序保存 |
| 环境 `environment` | 教学代码库、测试定义和运行结果 | 外部系统或本地工具 |
| 状态 `state` | 当前目标、已读信息、步骤数、结束状态 | 程序维护 |
| 策略 `policy` | 根据已有信息决定下一步 | 真实 Agent 通常由 LLM 承担部分职责 |
| 动作 `action` | 检查测试、读取函数、返回结论 | 策略提出，程序检查并执行 |
| 观察 `observation` | 测试期望 80，实际 20 | 环境返回 |

这里的状态不是“模型脑中真实发生的一切”。我们只能控制与记录外部状态，例如消息、工具结果、预算和文件版本。

代码库真实状态也不等于模型已知状态。没读取的函数、被截断的日志、运行后改动的文件，都可能造成信息缺口。因此我们不能把一次模型输出视为完全了解环境后的最优动作。

## 2.3 用一个递推式理解循环

不用先学强化学习优化算法，也可以写出控制关系：

```text
context_t = build_context(goal, history_t)
action_t  = policy(context_t)
observation_(t+1) = environment.execute(action_t)
history_(t+1) = history_t + [(action_t, observation_(t+1))]
```

若模型参数固定，变化的是上下文、动作和外部状态，并不发生梯度更新。把观察放入下一轮上下文不是“训练模型”；把失败摘要存在文件里，也不自动等同于强化学习。

这个表达省略了真实系统中的验证、授权和超时。工程代码必须把它们补回来，不能因为公式简单就采用没有边界的 `while True`。

本章不要求模型输出完整思维过程。调试所需证据是：输入了什么、选择了什么动作、参数是什么、执行结果是什么、因为什么停止。可见解释可以辅助排查，但不能当作模型内部机制的可靠测量。

## 2.4 把状态机写清楚，再写代码

本章用四种结束结果：

```text
running ──有效的 finish──→ finished
   │
   ├──动作结构无效───────→ invalid_action
   │
   └──耗尽决策步数───────→ step_limit
```

`finished` 的含义是“运行器收到了完整最终答案”，而不是“答案已经被验证正确”。后面做代码修复时，还要有单独的评测字段，例如 `tests_passed`。

不要把“异常结束”“主动结束”和“测试通过”压缩成同一个 `done=True`。它们对应不同的失败分析，也决定下一次是否重试。

## 2.5 为什么先使用假的策略

直接接真实 LLM 时，输出有变化，网络也可能失败。刚开始发现循环不对，你不容易分清是控制代码错误、提示不清，还是模型选择不同。

所以本章使用一个确定性的 `scripted_policy`：第一次请求测试信息，第二次请求函数文本，第三次结束。它是用来测试运行器的替身，不具备自然语言理解与泛化能力。

这是工程测试中的依赖替换：先固定不确定的组件，验证数据流和终止逻辑；下一章再把替身换成真实模型。

因此本章演示不是一个已经实现推理能力的 LLM Agent。准确说，它是未来 LLM Agent 的控制骨架及其离线测试。

## 2.6 最小状态与运行器

完整代码：[ch02_loop.py](/assets/learning/llm-agent/ch02_loop.py)。核心状态如下：

```python
@dataclass
class AgentState:
    goal: str
    history: list[dict] = field(default_factory=list)
    steps: int = 0
    status: str = "running"
    answer: str | None = None
```

`default_factory=list` 让每次运行拿到独立的历史列表。不同任务共用可变历史，可能导致上个任务的信息污染下个任务。

运行器的骨架是：

```python
for _ in range(max_steps):
    state.steps += 1
    action = policy(state)
    # 验证动作结构；无效则结束。
    # 若是 finish，验证答案并返回。
    observation = environment(action["name"])
    state.history.append({"action": action, "observation": observation})
# 尚未完成：标记 step_limit，而不是伪造最终答案。
```

这里故意把预算解释为“策略决策次数”。读测试算一次，读代码算一次，返回结论也算一次。否则不同实验可能一个计算工具次数，一个计算模型轮数，最后得到不可比的性能数字。

完整代码还区分了两类坏动作：

- 动作结构坏了，例如返回字符串而不是字典：结束为 `invalid_action`。
- 动作结构完整但名称不存在：返回可观察的错误，让策略有机会改正；错误动作仍消耗一步。

真实接口的结构校验会在第 3 章细化。

## 2.7 手工走一遍轨迹

执行：

```powershell
python assets/learning/llm-agent/ch02_loop.py
```

这次运行不调用 API，预期过程为：

| 决策步 | 动作 | 新增观察 | 状态 |
| --- | --- | --- | --- |
| 1 | `inspect_tests` | 期望 80，实际 20 | running |
| 2 | `inspect_code` | `return price * discount` | running |
| 3 | `finish` | 返回预设诊断 | finished |

本章 `environment` 返回的是写在代码里的教学观察，并没有实际运行测试。不要在实验笔记里写“测试已经执行”。第 3 章会读真实的教学文件，第 11 章才开放受限测试执行。

试着用自然语言逐步解释：为什么下一次策略调用能知道已经检查过测试？答案就在 `state.history` 的更新，而不是“模型会自己记住”。

## 2.8 三个故障实验

### 实验 A：少给一步预算

```powershell
python assets/learning/llm-agent/ch02_loop.py --max-steps 2
```

预期：`step_limit`，历史里有两次观察，但没有最终答案。

解释：程序已收集证据，却没有预算再做一次结束决策。这证明“工具执行完成”不代表“任务输出已经生成”。

如果业务允许，可以另设独立的收尾预算，但必须把它计入真实成本；本章不偷偷赠送额外一步。

### 实验 B：策略永远重复

```powershell
python assets/learning/llm-agent/ch02_loop.py --mode repeat --max-steps 4
```

预期：连续四次 `inspect_tests`，随后 `step_limit`。

练习：自行添加一个重复检测器。如果连续三次动作及参数相同，而且观察也没有变化，提前标记 `stalled`。但思考反例：轮询后台任务时，重复同一个动作可能是合理的。不要把“重复”绝对等同于错误。

### 实验 C：策略提出不存在的动作

```powershell
python assets/learning/llm-agent/ch02_loop.py --mode unknown --max-steps 3
```

预期：不存在的动作只得到错误观察，三步后退出。示例中的 `delete_everything` 只是一个未注册字符串，不会执行系统命令。

你要解释：为什么不对它调用 `eval()`？因为模型提出的字符串不具有执行授权；能执行的范围应该由程序明确定义。

## 2.9 预算不是只加一个 for 循环

本章的循环上限只约束决策步数。它不能中断一个永不返回的 `policy()` 或工具函数，也不能阻止一次动作读取过多内容。

后续要逐层补充：

- 单次模型调用超时与有限重试。
- 单次工具执行超时和输出大小限制。
- 整个任务的截止时间。
- 工具调用次数、Token 或费用预算。
- 出错时的取消与资源清理。

本章全是即时返回的本地模拟函数，因此不需要引入线程或进程取消机制。明确限制比把教学代码称为“生产级框架”更重要。

## 2.10 用控制变量做实验

本章不比较模型好坏，而是比较运行器行为。一次只改变预算或策略，保持其余条件不变。

| 运行配置 | 预期决策次数 | 预期结束原因 | 实际结果 |
| --- | --- | --- | --- |
| normal，预算 4 | 3 | finished | 自行填写 |
| normal，预算 2 | 2 | step_limit | 自行填写 |
| repeat，预算 4 | 4 | step_limit | 自行填写 |
| unknown，预算 3 | 3 | step_limit | 自行填写 |

检查历史长度为什么有时等于步骤数、有时少一次：本章 `finish` 消耗决策预算，但不产生环境观察。

可以请 Claude Code 做一次针对性审查：

```text
请检查我的 AgentRunner：所有失败路径是否消耗预算？
finished 是否被误当成测试通过？不同任务是否共享 history？
只指出问题与需要补的测试，不直接替我重写循环。
```

## 2.11 自测与通关

1. 一个写死了三次模型调用的程序，为什么未必属于自主 Agent？
2. 为什么模型的上下文不等于环境的完整状态？
3. 把工具观察加进历史，是否更新了模型参数？
4. 本章第三步为什么需要预算？
5. 有最大步数，是否就保证整个程序在固定时间内结束？

<details>
<summary>完成自测后查看参考要点</summary>

<p>1. 要看模型是否决定过程与动作，而不是调用次数。2. 模型只能看到被提供的信息，尚未读取、被省略或已变化的状态可能未知。3. 没有，这是上下文更新。4. finish 是一次策略决策。5. 不能，单次调用仍可能阻塞，需要另外设计超时与取消。</p>

</details>

通关任务：不看原代码，实现一个不同的小环境，例如“检查库存 → 查询替代品 → 返回建议”。仍使用模拟策略，但要能正常结束、耗尽预算，并处理未知动作。只改名字、原样复制不算完成迁移练习。

提交物：可运行代码、四组故障实验记录、一个你自行补充的测试，以及一段不用术语也能讲清控制循环的说明。

## 2.12 本章小结与学习账本

- 可信度：运行器行为可由离线测试确定；没有任何真实模型能力结论。
- 当前缺口：策略仍是脚本，环境仍是模拟；还缺真实工具协议与参数校验。
