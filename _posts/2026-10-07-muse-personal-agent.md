学完工具调用和记忆之后，再看个人 Agent 产品，我最想弄明白的是：**用户关掉应用以后，一个任务靠什么继续推进？**

Muse 可以作为理解这个问题的一个例子。这篇记录我对它的系统组成和任务流程的理解。资料核对日期：**2026-10-07**，依据 Meta 官方资料整理，尚未实际使用产品。

## 1. 先区分 Muse 和 Muse Spark

Meta 在 2026 年 9 月 8 日推出的 Muse 是个人智能体产品，Muse Spark 是驱动它的模型。Muse 运行在专属云端计算机 Muse Secure VM 上，可以通过独立应用或 WhatsApp 交流。发布公告中的上线范围为美国，支持 iOS、Android 和网页端。[发布公告](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)

我先用下面这个拆分帮助自己理解；这是学习用的概括，并非官方完整架构图：

```text
Muse
├─ 模型：理解目标、判断下一步
├─ 工具：浏览器、终端、文件与服务连接
├─ 记忆与任务状态：保存偏好和进展
├─ 后台执行：在需要时继续工作
└─ 权限控制：判断某个动作是否允许执行
```

这样看，模型能力只是整个任务系统的一部分。即使模型能想出合理计划，环境、工具或状态保存出了问题，任务仍然可能失败。

## 2. 用“帮我安排出差”走一遍

假设用户说：

> 下个月去上海出差三天，预算有限，帮我安排一下。

这个任务缺少日期、出发地和预算数字。第一步应当补足约束，然后再比较交通与住宿。为了理解执行过程，我把它拆成五段：

| 阶段 | 需要解决什么 | 应保留什么 |
| --- | --- | --- |
| 明确目标 | 日期、地点、预算是什么？ | 用户确认过的约束 |
| 获取信息 | 有哪些可选交通与住宿？ | 来源、价格与查询时间 |
| 比较方案 | 哪个方案更符合约束？ | 候选项与选择理由 |
| 执行操作 | 是否需要预订或支付？ | 授权与操作结果 |
| 后续跟进 | 条件变化后是否需要调整？ | 当前进展与待办事项 |

这是我构造的教学例子，不能当作 Muse 的实测。它帮助我看到：一次任务可能跨越多次模型调用、工具操作和用户确认。

据官方设计文章，Muse 拥有文件系统、终端和浏览器，能制作文档或网页，并依据日程和相关事件继续工作。[产品设计说明](https://introducing.muse.ai/)

## 3. 记忆和任务状态，分别记什么

学习时，我想把这两类信息分清楚：

```text
用户偏好：倾向早班交通，住宿希望靠近目的地
任务状态：已经比较三家酒店，尚未确定日期，还没有预订
```

偏好可以帮助后续任务；任务状态则帮助当前工作继续推进。即使聊天记录还在，也不代表系统已经清楚保存了“哪些做完、哪些待做”。这是我分析长期任务时采用的区分，并非对 Muse 内部数据结构的描述。

官方披露，Muse 的记忆可以跨对话保持，用户能够阅读和编辑记忆文件，也可以查看活动日志。[记忆与活动记录](https://introducing.muse.ai/)

一个值得记住的边界：系统推断出的偏好不应随意当作用户确认过的事实。比如用户某次选了便宜酒店，未必代表以后永远只关心价格。

## 4. 后台执行需要知道什么时候继续、什么时候停

官方介绍中，Muse 可以在关闭应用后继续处理工作；出现有意义的新信息或需要用户输入时，再发送提醒。[后台任务说明](https://introducing.muse.ai/)

我把这里的逻辑理解成一个任务循环：

```text
读取目标和当前进展
→ 判断下一步
→ 执行工具或等待事件
→ 记录结果
→ 继续 / 等待用户 / 完成 / 停止
```

这个循环与之前学的 Agent 控制循环能对应起来，只是生命周期变长了。需要额外考虑：外部信息何时过期，失败后能否重试，怎样避免重复操作，以及任务已经失去意义时是否应停止。

这些是从任务形态推出来的工程问题，官方功能介绍本身不能证明每种情况都处理好了。

## 5. Sentinel 为什么要单独存在

据 Meta 技术说明，Sentinel 是独立的权限控制组件，负责连接器操作和网络出口授权。凭据服务与智能体执行环境分离，实际凭据可在通过授权后于网络边界插入；必要审批直接交给用户客户端。[安全架构说明](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

我对这部分的理解是：一个动作至少要回答两个问题。

| 问题 | 关注点 |
| --- | --- |
| 这个动作是否有助于完成任务？ | 任务决策 |
| 当前身份和授权是否允许这个动作？ | 权限判断 |

“帮我比较酒店”并不自然包含“可以付款”。所以权限应落到具体操作和范围上，不能只依赖模型记住一句口头要求。

## 6. 把概念对应到官方披露的实现

继续读技术说明后，可以补上几个具体组件：执行循环由名为 Hatch 的常驻程序承载；内置连接器通过服务 API 和使用说明接入工具；浏览器有专门的子智能体；定时任务和事件让工作在对话之外继续。官方同时披露了持久化状态存储，但没有给出完整任务调度与记忆检索算法。[技术说明](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

我把执行关系整理成下面的教学流程；箭头说明职责关系，不代表官方源码中的具体调用顺序：

```text
用户消息 / 定时触发 / 相关事件
→ 执行程序组织当前目标、记忆和工具结果
→ 模型决定下一步
→ 权限检查后调用连接器、浏览器或终端
→ 记录观察和进展
→ 再次决策，或等待、结束
```

这里我最想记住的是：模型推理与任务生命周期属于两层。所谓持续工作，可以由后台程序按需再次调用模型来实现；没有必要把它想象成模型始终在不停生成 token。

## 7. 个人数据从哪里来

先按用途梳理运行时数据，避免把“知道我的偏好”直接等同于“用我的资料训练过模型”：

| 数据 | 获取入口 | 在任务中的作用 |
| --- | --- | --- |
| 用户指令与上传材料 | 对话、文件上传 | 明确目标、约束和待处理内容 |
| 已授权服务的信息 | 邮箱、日历等连接器，以及支持的 Meta 应用 | 查询个人日程和相关内容 |
| 当前外部信息 | 搜索、浏览器、服务 API | 获取任务需要的新信息 |
| 记忆与任务记录 | 之前交互及执行过程中保存的内容 | 延续偏好和任务进展 |

这些入口依据官方发布与产品设计说明整理；具体可读取什么取决于连接情况和授权范围。[发布公告](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)、[产品设计](https://introducing.muse.ai/)

用出差例子检查来源就很直观：预算来自用户，空闲时间来自授权日历，酒店报价来自本次查询，候选方案来自先前任务记录。每个结论最好都能回到相应来源，也要区分过期信息和当前信息。

## 8. 模型训练数据又来自哪里

这里要分清两件事：个性化可以通过读取外部记忆和资料实现；模型能力提升则涉及后续训练和参数更新。前者并不要求为每个用户单独训练模型。

Meta 已披露部分 Agent 训练方法：Muse Spark 1.3 在多种执行框架和长任务中训练；1.2 的编码训练包含筛选后的执行轨迹，以及模型生成的环境、指令和候选解评分。但这是特定版本与领域的披露，不能推广成全部 Muse 的完整训练配方。[1.3 训练方向](https://research.meta.ai/blog/introducing-muse-spark-1-3)、[1.2 训练说明](https://research.meta.ai/blog/introducing-muse-code-and-muse-spark-1-2)

用户数据也有单独政策：官方称，对话、工具调用和子智能体交接轨迹可在移除关键个人标识信息后用于训练后续模型，用户可在设置中退出。这与“个人资料在当前任务中被读取”是不同的数据用途。[数据政策](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

截至这次查阅，我没有找到足以确定 Muse Spark 全部预训练语料来源、各类数据比例和完整处理流程的公开资料。因此，不能把猜测的数据集写成已确认事实。

## 9. 下次体验时，我会观察什么

我会先选一个结果容易检查的小任务，看看它能否保存约束、给出证据、报告真实执行结果。然后再观察中断后恢复、记忆修改和权限撤销的行为。

对个人 Agent，我暂时最关心这三个问题：

- 能区分“已经完成”和“准备去做”吗？
- 任务卡住时，能说清楚缺少什么吗？
- 主动联系用户时，是否带来了值得处理的新信息？

读 Muse 资料的收获，是开始把个人 Agent 看成一套长期运行的任务系统：模型、工具、状态与权限需要一起工作。
