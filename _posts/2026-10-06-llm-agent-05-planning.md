第 4 章的循环每次根据现有证据选择下一步，适合逐步调查。但当任务变成“核对业务规则、实现和测试，再给出修改方案”，你还需要知道哪些子目标已完成、哪些依赖尚未满足。

本章回答：**怎样把计划变成能检查、能执行、能修订的数据结构？**

建议用时 5 小时：模式与计划设计 60 分钟、实现和阅读代码 90 分钟、故障实验 90 分钟、迁移作业和复述 60 分钟。

系列导航：[第 4 章：ReAct](/notes/llm-agent-04-react/) → **第 5 章** → [第 6 章：上下文工程](/notes/llm-agent-06-context-engineering/)。[实验说明](/assets/learning/llm-agent/README.md)

## 5.1 什么问题需要计划

“先分析，再修复，最后验证”是一段意向，尚不足以驱动执行器。程序还需要可定位的任务、依赖、输入输出，以及失败时的处理方式。

例如“验证完成”到底是读取了测试文件，还是实际执行了测试，抑或所有回归测试通过？这三个动作不能用同一个状态代替。

我们仍只开放第三章的只读工具。因此今天的计划只负责收集证据，执行器的 `completed` 表示证据步骤执行成功，不表示诊断正确，更不表示补丁通过测试。

这个限制让你专注于调度结构，同时保持整个系列的能力边界一致。

## 5.2 从简单路径到动态分解

Anthropic 的工程文章讨论了提示链、路由、并行、协调者与工作者、评估与优化等组合方式；这些是工程模式，不是一个有固定步骤的万能算法。[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)

以下是这些模式在本课程中的具体用法：

| 模式 | 例子 | 控制权与主要代价 |
| --- | --- | --- |
| Prompt Chaining | 提取规格 → 检查规格 → 生成实现建议 | 程序预设顺序；前一步错误可能传递 |
| Routing | 文档问题走检索，代码问题走仓库工具 | 先做选择；错误路由可能遗漏必要能力 |
| Parallelization | 分别阅读业务定义和测试约束 | 独立任务可并发；汇总仍要处理矛盾 |
| Evaluator-Optimizer | 生成补丁 → 外部测试 → 修改补丁 | 反馈推动改进；验证器可能不完备 |
| Orchestrator-Workers | 根据任务动态拆出不同调查子任务 | 动态协调；管理和上下文开销增加 |
| Plan-and-Execute | 先产出任务结构，再调度与调整 | 计划显式化；环境变化会使计划过时 |

固定工作流同样有价值：一旦路径稳定，确定性编排通常更容易验证。不要仅因为有三次模型调用就把它称为多 Agent，也不要因为打印了计划就认为已经实现了规划器。

## 5.3 ReAct 与计划如何组合

可以把二者放在不同时间尺度：

```text
任务目标
  → 计划：需要哪些证据、子目标怎样依赖
  → 执行一个子目标：观察 → 选择动作 → 获得反馈
  → 更新任务完成状态
  → 必要时修订计划
```

但这不是必须的层级。小任务直接用单循环即可；大任务才可能从独立计划表示中获益。

必须避免两个常见误区：计划不是未来一定会发生的事实；计划越详细，也不代表推理质量越高。细到每次搜索关键词的长计划，可能在第一次读文件后就失效。

更稳妥的粒度是“收集哪类证据、产生什么产物、依赖谁”，而不是让模型预言全部工具返回值。

## 5.4 把任务表示为有向无环图

本课使用 DAG，即任务节点与有向依赖边构成的无环图。若 `A → B`，表示 B 必须在 A 成功后才可运行。

```text
                    ┌── code：读取实现 ──┐
spec：读取业务定义 ─┤                    ├── 人工或模型综合证据
                    └── tests：读取测试 ─┘
```

右侧“综合证据”是使用产物的下一阶段，不包含在本课三节点执行器内。两个子任务依赖 `spec` 是本课采用的调查顺序；文件读取本身并不天然要求这种依赖。练习中可以移除它，比较调度意义。

任务类型：

```python
@dataclass(frozen=True)
class Task:
    id: str
    tool: str
    args: dict
    deps: tuple[str, ...] = ()
```

每个字段都有明确用途：`id` 关联状态，`tool/args` 确定执行操作，`deps` 确定就绪条件。可读说明与验收标准可以后续扩展，但不能让模型用说明文字替代真实执行结果。

`frozen=True` 防止直接替换字段，却不会递归冻结字典。本课在运行与重规划边界复制任务数据，避免回调就地修改已保存计划。

## 5.5 执行前验证整个计划

验证器需要拒绝：

- 空计划或超过教学规模上限的计划。
- 空 ID、重复 ID。
- 未注册工具或不符合基本形状的参数。
- 不存在的依赖与自依赖。
- 依赖环，例如 A 等 B、B 又等 A。

检查环的一种简单方式是反复找就绪节点：

```text
已访问集合 = 空
循环：
    找出依赖都在已访问集合内的未访问节点
    没有这样的节点，但还有剩余节点 → 有环
    把就绪节点加入已访问集合
```

教学实现反复扫描列表，最坏约为 O(V² + V×E)，其中 V 是节点数、E 是依赖边数。真正的大图应使用维护入度与邻接表的拓扑排序，做到 O(V+E)。本课限制为最多 12 个节点，优先让逻辑便于阅读。

注意两层验证仍然分开：任务图验证保证依赖可调度；工具执行器还要检查参数内容与权限。一个没有环的计划，仍可能要求读取不允许的文件。

## 5.6 执行、失败和修订

代码：[ch05_planning.py](/assets/learning/llm-agent/ch05_planning.py)。它复用第三章的 `execute`，默认使用确定性的初始计划与修订函数，不调用 LLM。

```text
找就绪任务
  → 扣除一次共享执行预算
  → 调用工具
      ├── 成功：保存产物，标记 done
      └── 失败：记录错误
                 → 检查修订次数
                 → 提议新计划
                 → 验证图及已完成节点
                 → 在原预算下继续
```

本课只允许修订未完成任务的配置与依赖，保持全部任务 ID 集合不变。已完成节点不能被删除、改参数或改依赖；否则旧产物对应什么操作就不再清楚。

复杂系统可以支持新增子任务，但必须设计新的状态合并、取消和证据失效规则。限制修订范围，是为了让第一次实现可以审查。

失败一次后，不能重新创建一个拥有全额预算的运行器。否则名义上每次最多六步，外层重规划却可能无限继续。

## 5.7 三个可以复现的实验

### 实验 A：正常证据收集

```powershell
python -B assets/learning/llm-agent/ch05_planning.py
```

预期：`completed`，`attempts=3`，`revisions=0`。

程序先读规格，再顺序读取实现和测试。虽然后两者没有相互依赖，本课并不并发执行；可并行的图结构与实际并发调度是两回事。

### 实验 B：故障后修订

```powershell
python -B assets/learning/llm-agent/ch05_planning.py --fault
```

初始 `code` 任务引用 `missing.py`，被工具允许集合拒绝。脚本修订器将它改成 `pricing.py`，保留已完成的 `spec`，然后继续。

预期：`completed`，`attempts=4`，`revisions=1`。四次尝试分别是读规格、失败读取、修订后读取、读测试；其中没有把规格再读一遍。

修订器知道这个教学故障怎么修，是一个测试替身。它不从自然语言自主规划，也不会理解任意异常。控制流修复成功不能被写成“LLM 已学会重规划”。

### 实验 C：不允许修订

```powershell
python -B assets/learning/llm-agent/ch05_planning.py --fault --no-repair
```

预期：`repair_limit`，尝试两次，只有 `spec` 完成。系统保留已有证据并说明为什么停下，不伪造其余任务的成功状态。

再通过代码设置 `max_attempts=2` 跑故障计划：即使还允许一次修订，执行预算也已耗尽，最终应为 `attempt_limit`。这能帮助你区分修订预算与工具执行预算。

## 5.8 真正接上 LLM Planner 需要什么

扩展时可以让模型返回 JSON 任务列表，再解析为 `Task`。但不要把反序列化成功等同于可执行计划。

你需要另外完成：

1. 明确任务 JSON 的字段、类型、工具集合和依赖规则。
2. 解析后执行图验证、参数检查与资源预算检查。
3. 给 Planner 提供真实产物与错误类别，不只说“上次失败了”。
4. 把计划调用本身的次数、Token、延迟加入总预算。
5. 拒绝模型直接把 `done=true` 当作运行事实；完成状态只能来自执行器。

本章的 `max_attempts` 统计工具执行尝试，没有统计模型规划成本，因为当前实现没有调用模型。真正接入后必须扩展预算，不能沿用旧指标并声称总成本不变。

这也是为什么先实现可靠的运行器很重要：模型给出计划只是起点，执行过程仍由你的程序负责。

## 5.9 规划搜索：多想几条路线是否值得

单个计划可能一开始就选错方向。另一种思路是生成多条候选、评估它们，再保留部分路线继续展开。

Tree of Thoughts 研究了按文本中间状态进行分支探索、评估和搜索的思路。它与“让模型写更长的计划”不同，因为搜索显式管理了多个候选路径。[Tree of Thoughts 原论文](https://arxiv.org/abs/2305.10601)

把它迁移到代码诊断时，可以假设三个候选原因：业务含义错误、边界处理错误、测试预期错误。然后设计能区分它们的证据获取动作，而不是仅让三个角色重复同一句猜测。

搜索也有代价。若每层保留所有 b 个分支，深度为 d，候选规模会迅速增长；束搜索可以限制保留宽度，但评分器若偏好错误方案，就会过早丢掉正确路径。

本章不实现完整 ToT 或 MCTS，也不把启发式候选评分包装成可靠概率。迁移练习只需比较“一个计划”和“最多两个候选计划”，严格记录额外模型调用与验证次数。

## 5.10 怎样衡量计划质量

不要用计划长度评分。更有用的检查包括：

| 指标 | 它说明什么 | 注意事项 |
| --- | --- | --- |
| 图合法率 | 依赖结构是否可调度 | 不等于任务语义正确 |
| 关键证据覆盖 | 计划是否查到了规格、实现、测试等 | 不同任务的必要证据不同 |
| 完成尝试数 | 重复工作和失败重试的代价 | 必须计入失败调用 |
| 修订次数 | 初始计划是否频繁失效 | 少修订也可能意味着没有发现错误 |
| 最终任务成功 | 产物是否满足独立标准 | 不能让 Planner 自评代替外部验收 |

对当前教学题，完整证据收集是阶段里程碑；最终正确诊断仍要用第四章的评分与人工检查。图合法只是必要条件之一。

## 5.11 迁移作业与自测

迁移作业：在学习副本中实现一个计划修订器，让失败的“搜索不存在标识符”任务改为“列文件后读取候选”。这需要扩展当前的固定 ID 修订规则；先写清楚新增任务对旧产物有什么影响，再改代码。

至少测试：依赖环、缺失依赖、重复 ID、篡改已完成任务、修订后仍失败、预算用尽。真实模型规划可以作为第二阶段，先用固定提议验证图调度行为。

闭卷回答：

1. 为什么计划文本不是任务已经执行的证据？
2. 什么情况下两个节点可以并行？
3. 重规划时为什么保留已完成节点还不够，需要检查它是否被改写？
4. 为什么重新创建运行器可能突破原来的预算？
5. ToT 与单次生成多个计划的区别在哪里？

## 5.12 学习账本

- 本章变化：子任务、依赖、产物和修订被显式记录，失败后有有限恢复路径。
- 可信度：示例中的图与执行行为可以离线验证；LLM 规划能力尚未评测。
- 当前缺口：产物不断累积后，如何选择下一次模型调用真正需要的上下文？
- 掌握状态：待你完成一组新的依赖与修订实验，不以示例打印 completed 为标准。
