前三章已经能让模型读取教学文件。现在需要追问：**为什么读取一次文件之后，还要再次调用模型？这一轮增加了什么信息，会怎样改变下一步？**

这就是本章的中心。我们继续研究同一个折扣项目，用 ReAct 的思想组织调查，并设计能区分“多了信息”和“控制策略变好”的对照实验。

建议用时 4 小时：概念与论文 50 分钟、代码 50 分钟、对照实验 100 分钟、复述与迁移练习 40 分钟。

系列导航：[第 3 章：工具调用](/notes/llm-agent-03-tool-calling/) → **第 4 章** → [第 5 章：规划与工作流](/notes/llm-agent-05-planning/)。[配套代码与运行说明](/assets/learning/llm-agent/README.md)

## 4.1 从工具协议到决策策略

第三章解决的是协议问题：如何接收工具请求、执行允许的函数、把结果配对回传。协议正确，只能说明消息往返成立。

ReAct 关注的是如何交错使用推理与行动。原论文让语言模型生成推理片段和任务动作，并利用环境反馈继续推理与行动；它在问答、事实核查和交互任务中进行了实验。[ReAct 原论文](https://arxiv.org/abs/2210.03629)

论文提供的是特定模型、任务和实验设置下的证据，不是“任何系统加循环都会更好”的保证。学习时应把两个问题分开：

- **接口层**：一次工具调用能不能正确执行？
- **策略层**：当前最需要什么证据，选择这个工具是否合理？

今天的实验采用现代结构化工具接口，实现受 ReAct 启发的反馈循环，不逐项复现原论文的提示模板、模型与基准。它也不能证明 Claude Code 内部实现了某种特定算法。

## 4.2 推理、行动和观察各自改变什么

沿用 `final_price(100, 0.2)` 的问题：

| 环节 | 此时知道什么 | 合理的下一步 |
| --- | --- | --- |
| 初始目标 | 用户认为价格不对，但折扣定义可能含糊 | 查询业务约定 |
| 读到 README | `0.2` 表示减去 20%，应该付 80 | 查询实现 |
| 读到函数 | 返回 `price * discount`，按代码推算得到 20 | 查询测试约定或给出有限结论 |
| 读到测试 | 测试明确期望 80 | 解释金额含义混淆，建议修复公式 |

这里“按代码推算”与“实际执行测试”不同。前三章的工具集没有运行测试的能力，即便结论正确，也不能声称测试已经通过或失败。

一个有价值的中间决策摘要是：“缺少 discount 的业务定义，需要读 README。”它指出了信息缺口和接下来的证据来源。单纯说“让我仔细思考一下”没有提供同样的可检查信息。

可见解释不等于模型内部思维的完整记录。本课不要求输出隐藏思维链；调试主要依赖目标、动作、参数、工具结果、停止原因和最终证据。

## 4.3 把反馈写入循环

第 2 章的递推关系在这里具体化：

```text
历史 H_t = 目标 + 之前的动作与观察
动作 A_t = 模型根据 H_t 选择下一次工具调用或结束
观察 O_(t+1) = 执行器运行 A_t 后返回的结果
历史 H_(t+1) = H_t + A_t + O_(t+1)
```

关键不是循环的外形，而是 `O_(t+1)` 是否真的进入下一次决策。若每轮都发送原始问题而不带工具结果，虽然调用了很多次模型，也没有实现这个反馈机制。

同样，调用工具时把结果丢弃，或者忽略工具失败、仍沿着原先答案输出，都是“有行动、没有有效利用观察”的问题。

这时可以先查三件事：结果是否正确配对，下一次请求是否确实包含观察，策略是否具备修正或结束的选择。不要一上来把所有失败归为“模型能力不够”。

## 4.4 多走一步的收益与代价

本章用一个设计启发式判断下一步：

```text
行动价值 ≈ 对任务不确定性的预期减少
           − 延迟与调用成本
           − 动作副作用及失败风险
```

这是教学用的决策视角，不是原论文给出的可直接计算公式。你尚不知道真实的信息收益，只能通过经验、任务结构和实验估计。

例如：不知道折扣定义时读 README，可能消除关键歧义；已经完整读过未变化的 README，再读一次往往增加成本，却不增加证据。工具调用次数因此不是越多越好。

循环也有自己的失败模式：检索词选错、工具结果被截断、观察误读、不断重复、过早结束。每次失败都应映射到轨迹中的一个位置，而不是只记录“回答不好”。

## 4.5 为什么需要三组对照

如果只比较“完全不给代码的模型”和“能读代码的 Agent”，Agent 的优势可能主要来自多拿到了文件。要研究是否需要动态调查，应加入一个获得相同信息的简单方案。

本章安排三个模式：

| 模式 | 模型起始可见信息 | 工具 | 要回答的问题 |
| --- | --- | --- | --- |
| `blind` | 任务描述 | 无 | 没有证据时是否会诚实承认未知？ |
| `provided` | 任务 + 全部三个教学文件 | 无 | 预先给齐信息，一次回答是否已经足够？ |
| `react` | 任务 + 工具定义 | 三个只读工具 | 按需读取是否能获得正确结论，代价是多少？ |

`blind` 是信息缺失对照，不是强基线。`provided` 才能帮助你判断这个小任务是否值得启用工具循环。

三组共用任务、最终输出结构和真实模式中的模型 ID。不过它们的输入长度、轮数和工具能力不同，所以这仍不是严格等计算量实验。报告必须保留这些差别，不能把结果全部归因于 ReAct。

后续更严格的实验可以控制总费用或 Token 预算，再比较成功率；也可以固定检索获得的证据，研究不同调查顺序和停止策略。

## 4.6 配套实现：复用第三章的执行器

代码：[ch04_react.py](/assets/learning/llm-agent/ch04_react.py)。下载时还需要 [ch03_tools.py](/assets/learning/llm-agent/ch03_tools.py) 和原来的 `fixtures` 目录，保持它们在同一实验目录。

```text
ch04_react.py
  ├── 构造三组输入
  ├── ask(messages)：真实模型或离线替身
  ├── ch03_tools.run_agent：预算、工具调用、历史更新
  └── grade：本题的有限评分器
```

最终答案要求为：

```json
{
  "expected": 80,
  "observed": 20,
  "formula": "price * (1 - discount)",
  "evidence": ["README.md", "pricing.py"],
  "verified_by_tests": false
}
```

这里展示的是本教学题的目标格式，不是实测模型输出。字段 `observed` 在本实验特指“阅读实现后推算的数值”，真实测试证据要另行获得。

评分器检查 JSON 结构、金额、公式、证据路径以及是否错误声称运行过测试。它还把答案引用的路径与实际提供或完整读取的文件集合比较，防止随便写出一个文件名就被认作有依据。

但这个评分器有局限：它采用规范化空白后的固定公式匹配，`price - price * discount` 这样的等价表达可能被误判；只通过搜索片段获得充分证据，也可能因为本题要求完整读取而得不到分。它不会验证引用文件中每句话是否真的支持结论。

所以必须同时查看原答案和轨迹。分数是筛查信号，不是对代码语义的完整证明。

## 4.7 先运行离线烟雾测试

在博客仓库根目录运行：

```powershell
python -B assets/learning/llm-agent/ch04_react.py
```

离线模式只测试输入组织、循环与评分管线。`blind` 的预设答案承认未知，另两组返回预设正确答案；`react` 分三次读取文件，然后结束。输出会明确标注 `scripted_offline`，`model` 和真实 `usage` 为 `null`。

预期控制行为：

| 模式 | 逻辑轮数 | 工具执行数 | 评分检查 |
| --- | --- | --- | --- |
| blind | 1 | 0 | 不满足本题完整诊断，但可诚实承认未知 |
| provided | 1 | 0 | 预设答案通过 |
| react | 4 | 3 | 预设答案通过 |

这个表不是模型性能数据。离线策略按已读取路径决定下一次读取，最终内容仍为脚本设定，不能泛化到新 Bug。

你应先尝试删除一个教学文件，观察工具错误是否让离线策略停止给出确定诊断。操作在实验副本中完成，恢复文件后再继续。

## 4.8 真实实验怎样运行与记录

完成第 1 章的环境与凭据配置后，显式运行：

```powershell
python -B assets/learning/llm-agent/ch04_react.py --live --mode provided
python -B assets/learning/llm-agent/ch04_react.py --live --mode react
```

使用你安装了 `anthropic` 的解释器；若用独立虚拟环境，替换命令中的 `python`。`--live --mode all` 会依次跑三组，可能产生多次计费调用。

每次运行记录 `model`、`status`、`rounds`、`tool_calls`、`usage`、`seconds`、`grade` 和 `trace`。耗时为整次逻辑运行的墙钟时间，成功收到的响应用量不等于所有异常重试的完整账单。

建议每组先重复 3 次观察波动；这只是熟悉实验，不能用三次运行宣称统计显著。模型可能直接回答、生成不合法 JSON，或用了过多轮数。保存这些失败，不只保留最好的一次。

为了评估迁移，你还要准备至少五个未出现在示例答案中的小任务，例如优惠券叠加、边界舍入、空输入、整数除法和单位转换。测试集答案放在评分器侧，不发送给 Agent，也不让 Claude Code 在调参过程中读取留出题答案。

## 4.9 读论文时抓住四个问题

阅读原论文的任务设置、方法和消融部分，控制在 40 分钟左右，写下自己的答案：

1. 哪些任务可以从环境拿到新证据？动作接口是什么？
2. 推理与动作怎样交错，哪些轨迹显示了反馈修正？
3. 基线获得的信息、工具与计算量是否相同？
4. 什么失败仍然存在，迁移到 Coding Agent 后可能更严重？

先区分论文中的实验证据与自己的迁移猜想。不要把旧模型上的历史成绩写成今天所选模型的预期成绩。

本课的算法判断是：当决定下一步所需的信息尚未获得时，反馈循环值得尝试；如果所有证据已经很小且明确，单次带上下文的调用可能更合适。是否如此要由任务上的质量与成本共同决定。

## 4.10 迁移作业与自测

迁移作业：在自己的实验副本中制作一个新故障，改写目标与独立评分器。保留 `provided` 对照，同时加入“读过同一未变化文件三次后停止”的策略实验。解释这种停止规则在哪些任务上可能误伤正常轮询。

闭卷回答：

1. 正确的 Tool Calling 为什么不自动保证好的 ReAct 策略？
2. 为什么不给代码与给工具的对比不足以隔离算法收益？
3. 一轮工具失败应怎样影响下一轮决策？
4. 任务成功率相同，为什么工具更多的方案未必更好？
5. 示例评分器最容易出现哪两类错误？

可交给 Claude Code 的审查任务：

```text
请审查我的三组对照是否存在信息泄漏、预算不一致或评分偏差。
先让我解释每组控制了什么，再指出不能由现有数据得出的结论。
不要替我编造实验数据，不要接触留出任务的答案。
```

通关要求：能解释一次反馈如何改变后续动作，跑通三组管线，并用一份失败轨迹区分工具层与策略层问题。未做真实调用时，只记录“离线机制验证完成”。

## 4.11 学习账本

- 本章变化：从能调用工具，推进到解释工具调用的价值，并建立基本对照。
- 可信度：ReAct 方法有原论文依据；本课实现是教学改编。离线结果不支持模型能力结论。
- 当前缺口：多步目标的依赖、完成条件和重规划还没有独立表示。
- 掌握状态：待实验与迁移作业，不因获得一个正确答案自动通关。
