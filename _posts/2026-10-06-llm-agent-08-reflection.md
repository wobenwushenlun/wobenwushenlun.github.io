第 7 章让经验能被保存下来。但如果保存的只是“下次要更仔细”，下一次决策未必会改变；如果经验本身错了，持久化反而扩大错误。

本章回答：**失败之后应反馈什么，怎样修正，怎样知道修正是真的改进，又该在何时停止？**

建议用时 4 小时：概念与论文 60 分钟、代码 50 分钟、反馈与过拟合实验 85 分钟、迁移与复述 45 分钟。

## 8.1 先把“再试一次”拆成四种机制

| 机制 | 下一次增加什么 | 可能的问题 |
| --- | --- | --- |
| 独立重试 | 另一个候选样本 | 可能重复同样错误 |
| 自我反馈 | 对当前候选的批评 | 批评本身可能错误 |
| 外部反馈修正 | 测试、编译或环境产生的失败证据 | 验证覆盖范围可能太小 |
| 反思记忆 | 对失败的解释、适用范围与下次检查步骤 | 错误解释可能长期传播 |

它们可以组合，但不要把任何第二次调用都叫作 Reflexion，也不要把一次测试失败后的重试叫作模型训练。

本章最重要的区分是：**Actor 提议，Critic 分析，Verifier 检查。** 同一个 LLM 可以扮演前两个角色，但这并不让它的意见成为独立的正确性证据。

## 8.2 两篇论文分别强调什么

Self-Refine 研究由模型产生初始输出、给出反馈、再迭代修改的方式，重点在测试时的反馈与修订，不需要为这套过程额外训练模型。[Self-Refine 原论文](https://arxiv.org/abs/2303.17651)

Reflexion 则将任务反馈转成语言形式的反思，并维护情景记忆以影响后续尝试。它强调通过语言反馈而不是更新权重来改进后续行为。[Reflexion 原论文](https://arxiv.org/abs/2303.11366)

论文中的历史基准成绩只对应各自实验设置。今天你使用的模型、提示、工具和预算不同，不能把那些数字当成课程预期收益。

两种思路的共同启发是：让下一次输入包含能改变行为的信息。区别可从反馈来源、是否跨尝试保留反思、怎样判定成功等方面分析，不需要靠名字猜测实际实现。

## 8.3 外部反馈应足够具体

对折扣题，比较两种反馈：

```text
弱反馈：答案不对，再想想。

具体反馈：输入 price=100、discount=0.2，期望 80，实际得到 20。
业务规则：discount 是减去的比例；当前候选返回了减免额。
待检查：无折扣时应付原价，全额折扣时应付 0。
```

后者把观测、规格解释和下一次检查分开。实际值与期望值来自验证器；“返回了减免额”是对实现的解释；“应检查哪些边界”是修订建议。

解释仍可能错。比如测试期望本身有缺陷、业务定义改变、单位不一致，都可能让看似明确的反思走偏。因此要保存反馈来源，不把 Critic 的所有文字标记为事实。

## 8.4 最小有限修正循环

```text
生成候选
  → 验证候选
      ├──通过公开验收 → 冻结候选 → 单独审计
      └──失败 → 若还有预算，记录失败与修订假设
                    → 生成下一候选
遇到非法候选、重复停滞或预算耗尽 → 明确停止
```

需要独立记录三个计数：候选提议次数、实际验证次数、反思次数。相同候选再次出现时可以因为停滞而跳过重复验证，但它仍消耗了一次提议预算。

若候选通过当前公开测试，本例立即冻结它，不为了“看起来更好”无休止修改。更复杂的任务可以采用独立评分选优，但也要保留已验证版本，避免最后一次修改比之前更差。

## 8.5 教学实现只执行可信算术

代码：[ch08_reflection.py](/assets/learning/llm-agent/ch08_reflection.py)。本文件只依赖 Python 标准库，可单独运行。

本课还未进入第 11 章的代码执行环境，因此不执行模型生成的 Python，也不改写教学仓库。程序提供三个宿主写好的候选：

| ID | 固定计算 | 含义 |
| --- | --- | --- |
| saved_amount | `price * discount` | 减免额，作为错误起点 |
| constant_80 | 始终返回 80 | 对一个样例的硬编码 |
| payable | `price * (1 - discount)` | 当前规格下的应付金额 |

Actor 返回的是候选 ID，而不是可执行文本。执行器只接受这个有限集合，使用 `Decimal` 做十进制计算，不调用 `eval` 或 `exec`。

这使得教学验证器能够真正计算不同输入下的结果。与第三章的“阅读测试文件”不同，这里确实进行了固定算术检查；但它不是执行原仓库的测试文件，也不是完成了一次任意代码补丁修复。

采用 Decimal 是为了让这几组有限小数案例易于比较。本章没有实现真实货币系统的币种、舍入、税费与优惠叠加规则。

## 8.6 反思记录不是自我表扬

示例记录的字段包括：

```text
failed_candidate：哪个候选失败
evidence：具体失败输入、期望值与实际值
hypothesis：错误机制的解释
next_check：下一次需要补充的检查
scope：结论适用的业务范围
verified：反思本身是否已被确认
```

固定反思器会写出“应付金额与减免额混淆”的教学假设，`verified` 仍为 false。修正候选通过一些测试，不代表整段自然语言解释的每句话都已经被证明。

想把反思存入第 7 章记忆库，应先作为候选记录，并附上题目范围、来源版本与失败证据。不要只把“最后成功”写成一个永久通用规则。

反思没有必要越长越好。长篇自责可能挤掉实际失败输入；真正值得保留的是下一次会怎样改变决策，以及这种改变有什么依据。

## 8.7 三种故障实验

### 实验 A：反馈后切换候选

```powershell
python -B assets/learning/llm-agent/ch08_reflection.py
```

预设 Actor 先选择 `saved_amount`；失败后看到非空反思列表，改选 `payable`。预期 `public_passed`，提议两次、验证两次，并通过独立算术审计。

必须如实描述：这个 Actor 没有理解反思文字，它只检查列表是否非空，修订路线是脚本写好的。演示验证的是反馈存储与有限循环，而不是语言反思带来了学习增益。

### 实验 B：反复提交相同候选

```powershell
python -B assets/learning/llm-agent/ch08_reflection.py --mode repeat
```

Actor 始终返回 `saved_amount`。第一次验证失败，第二次提议发现相同 ID，结束为 `stalled`，不重复做相同验证。

这条规则只在候选标识准确、验证确定性、环境没有变化时成立。若外部服务稍后可能恢复，同一个动作的重试可能有意义；不能把本题规则直接推广到所有 Agent。

### 实验 C：只记住一个答案

```powershell
python -B assets/learning/llm-agent/ch08_reflection.py --mode overfit
```

这个模式故意把公开验收缩小为 `(100, 0.2) → 80`。Actor 提交 `constant_80`，公开验收通过，但冻结后的审计会在其他价格或零金额案例上失败。

最终报告同时保留 `status=public_passed` 与 `audit.status=failed`。不要只展示第一个字段就宣布修复成功。

这些模式采用不同的脚本策略，其中 overfit 还故意改变了公开测试集，因此它们不是比较算法优劣的公平性能实验，而是暴露不同失败机制的教学场景。

## 8.8 公开测试与最终审计怎样分离

本章公开检查包括常规、零折扣和全额折扣。审计包含不同原价、零金额和另一折扣比例。审计结果只在候选冻结后计算，不回传给修正循环。

但所有案例都公开在源码里，所以这里的“审计”只是流程隔离，不是真正保密的留出集，也不具备无数据污染的基准含义。

当你做正式评测，应把留出任务与答案放在独立评测侧。开发时如果读到了它们并据此调整提示或候选，不能再称它们为未见数据。通过更多样例也不构成对所有输入的数学证明。

评分器的可靠性决定反思上限。若它只检查输出包含“80”，生成器学会迎合这个词就可能得分；若它允许修改验收标准，Agent 可能把问题“解决”为降低要求。

因此验收标准与生成候选必须由不同的权限路径维护，生成器不能随意改分数规则。

## 8.9 真正用模型反思时怎样做对照

下一阶段将固定 Actor 和反思器替换成模型调用，可以比较：

| 组别 | 反馈 | 尝试数或总预算 |
| --- | --- | --- |
| 单次生成 | 无 | 基础参考 |
| 多次独立采样 | 无跨次信息 | 与迭代组匹配预算 |
| 原始反馈修正 | 测试输入与结果 | 计入全部调用 |
| 反馈 + 反思 | 测试结果与失败摘要 | 还要计入反思调用成本 |

如果反思组比单次生成更好，只能说明整个额外计算流程有用，不能单独证明“语言反思”是原因。它还需要与相同预算下的独立重试、直接反馈对照。

记录每次候选、反馈、反思、用量与停止原因。报告任务级成功率和总成本，不把一次任务的五次尝试当成五个独立任务样本。

也要检查修正是否破坏原本正确的部分。对真实 Coding Agent，回归测试和改动范围审查同样重要，不能只盯着最初失败的断言。

## 8.10 如何接入当前系列

把它放回现有架构可以看成：

```text
第 5 章计划器：决定现在要验证哪个子目标
  → 第 4 章行动循环：获取证据并提出候选
  → Verifier：产生可检查反馈
  → 本章修正循环：在共享预算内决定是否继续
  → 第 7 章记忆：保存经过审核、有作用域的失败经验
```

这是一张接口关系图，不表示配套文件已经实现全部整合。当前 `run_revision` 使用固定函数与内存中的反思列表；跨进程存储、真实模型接口与任意代码执行需要后续接入。

整合时最容易遗漏的是总预算：外层任务预算、修正次数、工具调用次数和每次模型输出限制不是同一件事。新增一层循环，就检查它是否能绕开外层的停止条件。

## 8.11 迁移、自测与 Claude Code 用法

迁移作业：新增一个可信候选，专门在非整数原价时出错，再设计能暴露它的测试。先让它通过一组不足的测试，再展示审计如何揭露缺陷；不要改执行器为任意表达式求值。

闭卷回答：

1. 自我批评为什么不一定是独立证据？
2. Reflexion 与更新模型参数的训练有何不同？
3. 为什么公开测试通过后仍可能审计失败？
4. 什么时候重复候选可以直接判定停滞？
5. 如何判断改进来自反思而不是更多计算？

## 8.12 学习账本

- 本章变化：失败后的下一次尝试有了具体反馈、反思记录与明确停止条件。
- 可信度：可信算术与控制逻辑可离线验证；Self-Refine、Reflexion 提供方法来源，本例不复现其模型成绩。
- 当前缺口：当不同角色负责调查、生成和审查时，消息怎样传递、矛盾怎样解决？
- 掌握状态：待过拟合反例与迁移测试；跑通默认修正路径不是完整能力证明。
