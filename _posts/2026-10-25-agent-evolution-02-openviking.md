## 1. 问题：Agent 的上下文为什么越做越乱

一个长期研究 Agent 可能同时拥有：PDF 与网页、向量库中的文档片段、聊天摘要、用户偏好、失败经验、可执行脚本和 skills。它们往往分散在不同系统里，检索接口、身份范围、更新时机和来源记录也各不相同。

真正的困难包括：

- 不知道某条内容究竟是外部知识、用户事实还是经验规则。
- 向量命中一个片段，却不知道它属于哪个项目与版本。
- 为防遗漏而加载太多历史，造成成本和干扰。
- 记忆更新了，索引和摘要却仍然是旧的。
- 出错后难以追踪“最终输入为什么包含这些内容”。

OpenViking 将知识、记忆、技能放入可寻址的上下文系统，以目录、语义摘要和检索接口管理它们。它是上下文基础设施，不能仅因带有 benchmark 就归类成通用评测平台。[官方项目](https://github.com/volcengine/OpenViking)

## 2. 三类上下文，解决三种不同问题

| 类别 | 回答什么 | 教学例子 | 更新来源 |
| --- | --- | --- | --- |
| Resource | 有哪些外部资料 | 财报、论文、API 文档 | 导入、刷新、显式修改 |
| Memory | 从交互中知道了什么 | 用户偏好、项目进展、执行经验 | 会话与任务反馈 |
| Skill | 一类事情怎样做 | 抽取 PDF 表格的步骤和脚本 | 编写、整理、修订 |

项目将这三类内容统一管理；记忆的身份与命名空间有具体规则，不能凭概念图随意假定路径。[上下文类型](https://docs.openviking.ai/en/concepts/02-context-types)

教学上还应额外区分“任务状态”和“长期记忆”：前者记录当前任务已经做到哪里，后者影响以后任务。二者可以共享存储基础，但生命周期、恢复和正确性要求不同。

## 3. viking URI：让上下文有稳定地址

可以把 `viking://` 理解成系统内部的逻辑寻址方式。它不是一个自动可由公网浏览器打开的 HTTP 链接，也不代表数据必然存成同名本地文件。

下面是教学目录，不承诺每个命名空间都是当前默认：

```text
viking://resources/research-project/
├─ reports/
│  ├─ .abstract.md
│  ├─ .overview.md
│  └─ annual-report.md
└─ methods/
   └─ table-extraction.md

用户命名空间
├─ memories/
│  ├─ preferences/
│  └─ events/
└─ skills/
   └─ verify-report-numbers/
```

这种组织方式的价值，是上下文可以按项目、主题和身份定位。路径也会进入引用、调试与更新流程，因此重命名、迁移和访问控制都需要明确规则。[官方架构](https://docs.openviking.ai/en/concepts/01-architecture)

### 3.1 “可浏览”不等于“可信”

目录和 URI 帮助找到内容，不能证明内容真实。恶意网页可以成为 resource，模型编造的经验也可能进入 memory。应用仍需保存来源、时间、身份与证据等级。

## 4. L0 / L1 / L2：逐步披露信息

当前文档把它们定义为：

| 层级 | 内容 | 主要用途 |
| --- | --- | --- |
| L0 | 目录的短摘要 | 快速判断相关性 |
| L1 | 目录的概览与导航 | 理解覆盖范围、选择内容 |
| L2 | 正文、原始内容或解析后的主体 | 精读、引用与验证 |

需要注意，L0/L1 是**目录级语义侧文件**，不能简单说成“每个普通文件都必定附带三级副本”。PDF 经导入后可能成为 Markdown，L2 也不必保持源文件格式。[层级文档](https://docs.openviking.ai/en/concepts/03-context-layers)

### 4.1 为什么可能省 token

假设有 100 份报告，每份正文很长，任务只需要其中两份。先读目录摘要，再选择相关正文，可能减少无关输入。

但这只是机制推导。真实收益取决于：摘要是否遗漏关键词、查询是否足够明确、层级访问次数、模型是否错误停留在摘要，以及前置摘要生成成本。

### 4.2 最危险的误用：拿摘要当证据

“现金流受到资本开支影响”可以是目录概览，却不能替代原文中的数字、报告期和口径。涉及精确结论时，应回到 L2 并保留原始来源引用。

### 4.3 一致性问题

若 L2 更新、L1 未更新，Agent 可能基于旧摘要跳过新内容。因此需要记录正文版本与摘要生成状态；异步加工场景中，“已接收”不等于“所有衍生数据已可检索”。

## 5. 从导入到使用，走一遍链路

以下是根据官方架构概括的职责流，不是逐函数调用图：

```text
资源导入
  → 解析 / 建目录
  → 语义处理队列
  → 生成摘要与索引
  → VikingFS 与检索服务
  → 按任务召回
  → 读取正文并装配上下文
```

会话是另一条路径：

```text
交互记录
  → 会话提交 / 归档
  → 记忆抽取
  → 持久化到正确身份范围
  → 后续任务检索
```

架构文档划分了客户端、HTTP 服务、业务服务、解析、会话、检索与存储职责。[架构说明](https://docs.openviking.ai/en/concepts/01-architecture)

工程上应逐一验证：导入失败能否重试、任务完成语义是什么、同一资源重复导入如何处理、摘要生成失败是否可见、会话提交后多久能查到新记忆。

## 6. 一个必须注明的版本边界：不是所有“分层”都等于递归检索

项目材料中会看到目录组织和分层检索的表述。但是截至本文核对的文档，当前 `HierarchicalRetriever` 的职责是**全局向量检索，并可对召回候选重排**；检索不按目录逐层递归。

可以通过目录范围、上下文类型、权限、元数据与层级限制搜索；这些约束与“搜索算法逐目录递归”是两件事。[当前检索文档](https://docs.openviking.ai/en/concepts/07-retrieval)、[固定版本源码](https://github.com/volcengine/OpenViking/blob/4ab22a4923452362b60aef2826c2083ce36168d2/openviking/retrieve/hierarchical_retriever.py)

学习时应拆开三种层次：

1. **存储层次：** 内容按目录组织。
2. **语义层次：** 同一范围存在摘要、概览与正文。
3. **算法层次：** 检索器究竟怎样召回、过滤与排序。

不能从类名或架构图直接推断第三点。这个例子也说明：读开源系统要固定版本，并检查实现。

## 7. find 与 search：差别在哪里

当前文档中，`find` 是不使用会话意图分析的直接查询；`search` 可在提供会话且启用分析时，用会话内容规划查询，再执行检索。`search` 不保证永远需要额外模型调用，也不保证永远比 `find` 更好。[接口语义](https://docs.openviking.ai/en/concepts/07-retrieval)

以下示例要求已配置有效的同步 SDK 客户端 `client`，没有在本文环境连接服务执行：

```python
# 直接检索：先明确范围。
result = client.find(
    query="现金流量表中的资本开支口径",
    target_uri="viking://resources/",
)

# 语义层级访问：先概览，确有需要再打开正文。
overview = client.overview(uri="viking://resources/research-project")
body = client.read(
    uri="viking://resources/research-project/reports/annual-report.md"
)
```

真实项目应处理 URI 不存在、资源尚未就绪、权限不足和返回结构差异。代码示例表达的是调用职责，不是完整可运行项目。

### 7.1 查询规划的隐性成本

把一句查询拆成多个查询，有时提高覆盖率，也可能扩大结果、重复召回并增加延迟。应用应重新去重、按证据预算截断，不能把多查询结果直接全部交给生成模型。

## 8. 和 VikingMem 论文怎样对应

相关论文是 [VikingMem: A Memory Base Management System for Stateful LLM-based Applications](https://arxiv.org/abs/2605.29640)，本文参考 v3。论文提出 Memory Base 管理范式，用事件与实体组织长期状态，并讨论记忆抽取、演化、时间压缩和召回。

可用一个自拟例子理解事件与实体的区别：

```text
事件：10 月 20 日，某项目将接口版本由 v1 升为 v2。
实体：该项目当前接口版本为 v2。
```

事件保留变化发生的过程，实体描述某种聚合状态。若只有实体最新值，就很难回答“当时是什么”；若只有事件流，回答当前状态可能要反复计算。

这是一种值得借鉴的数据建模思路，但不能据此声称 OpenViking 的全部路径都实现了论文的完整算法。项目公开范围、底层引擎、配置和实验基准必须分别核对。

### 8.1 如何读论文实验

先记录数据集、抽取模型、检索模型、问题类型、记忆规模、存储成本和各阶段延迟。论文中的最高增益不能替代所有任务的平均增益；记忆问答效果也不能自动外推到工具执行成功率。

## 9. 为研究 Agent 设计一套可验证的记忆

下面是本文建议的应用层结构，非项目内置 schema：

```json
{
  "kind": "experience",
  "scope": "report-analysis",
  "trigger": "同一报表中同时出现本期和上期数据",
  "lesson": "计算前明确列名、单位和合并口径",
  "evidence_ids": ["trace-17", "trace-29"],
  "valid_from": "2026-10-25",
  "status": "candidate"
}
```

比起“以后仔细一点”，这个结构明确了触发条件、具体动作、证据和状态。候选经验应通过后续任务检验，不能抽取后立刻当成普遍规则。

事实型记忆也需要区别用户陈述、模型推断和已核验来源。“用户说 A”与“A 已被证明”是不同命题。

## 10. 怎样设计公平实验

**教学假设：** 分层上下文组织可以在相同答案质量下减少输入成本。

| 对照组 | 内容组织 | 生成模型 | 证据预算 |
| --- | --- | --- | --- |
| A | 普通 chunk RAG | 固定 | 固定 |
| B | 相同内容，加目录与摘要 | 固定 | 固定 |
| C | B 加查询规划 | 固定 | 固定 |
| D | C 加跨任务经验 | 固定 | 固定 |

分组目的是分别回答目录、摘要、规划和经验的贡献。不能 A 用旧文档、D 用更新资料，然后把全部增益归给记忆系统。

### 10.1 至少记录两套成本

- **在线成本：** 查询分析、检索、重排、正文读取、答案生成。
- **摊销成本：** 文档解析、摘要构建、embedding、更新、存储和失效处理。

若前期加工花费较大但资料会被重复使用，摊销后可能划算；若资料只使用一次，结论可能相反。

### 10.2 核心指标

任务通过率、证据召回、引用准确率、上下文 token、端到端延迟、错误身份召回率、旧知识误用率和冷启动加工耗时。还应单列“正确证据已召回但答案仍错”的情况，避免把生成模型的问题都算给检索。

## 11. 六类值得专门测试的故障

| 故障 | 注入方式 | 观察什么 |
| --- | --- | --- |
| 摘要遗漏 | 把关键限制放在正文小节 | 是否仍能读取正文 |
| 版本滞后 | 更新文档后立即查询 | 摘要与索引的一致性 |
| 记忆冲突 | 先旧版本，再新版本 | 当前事实与历史事实的区分 |
| 身份串扰 | 两个用户提供相反偏好 | 是否越过身份边界 |
| 经验过拟合 | 只在一类文档形成规则 | 是否损害其他类型任务 |
| 污染持久化 | 资源里夹带行为指令 | 是否被提炼成可信技能 |

这组测试是本文建议，不是官方声称全部通过的测试清单。

## 13. 一天 5 小时练习

| 时间 | 任务 | 产出 |
| --- | --- | --- |
| 45 分钟 | 阅读类型、层级、检索文档 | 三层概念边界图 |
| 75 分钟 | 导入一小组自有或公开资料 | 可浏览的目录与摘要 |
| 60 分钟 | 比较直接查询与会话规划 | 召回列表、延迟、token |
| 75 分钟 | 注入版本变化与相反用户偏好 | 可重复的失效案例 |
| 30 分钟 | 回看一次完整执行 | 来源到答案的证据链 |
| 15 分钟 | 闭卷讲解 | 为什么目录组织不等于递归检索 |

先打通小规模正确性，再扩大语料。不要用“成功导入”替代“能正确检索并完成任务”。

## 14. 自测与复习卡

1. Resource、memory、skill 的事实来源和更新方式有何不同？
2. 为什么 L1 概览不足以支持精确数值引用？
3. 如何判断目录分层与检索算法分层是否一致？
4. 查询 token 下降时，哪些成本可能被遗漏？
5. 怎样证明经验带来迁移，而不是测试题记忆？
