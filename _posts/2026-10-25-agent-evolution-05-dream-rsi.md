## 1. 先抓住一个问题：搜索策略本身也需要改进

设一个编码 Agent 要优化某段程序。每次提出改动、运行程序、得到分数都很贵。当有多个候选方向时，系统需要决定：继续优化哪条分支，开多少新分支，何时停止，以及怎样并行。

固定策略可能不断把预算浪费在低价值方向；但直接在线搜索更好的策略又很贵，因为评价一次策略，需要观察它如何影响一整段发现过程。

Dream-RSI 的关键想法是利用已经发生的搜索历史，把它变成可回放的有限世界，在其中低成本评估探索策略，再把选出的策略部署到新的在线搜索。[论文 v2](https://arxiv.org/html/2609.14858v2)

## 2. 三层对象：任务程序、发现 Agent、探索策略

| 对象 | 作用 | 在核心闭环中是否被修改 |
| --- | --- | --- |
| 候选程序 | 要优化的算法、kernel 等产物 | 在线发现时不断产生新版本 |
| 发现 Agent | 阅读上下文并编写候选程序 | 基础 Agent 保持固定 |
| 探索策略 | 决定在哪些方向花预算 | 离线阶段重写策略代码 |
| 任务评测器 | 验证并给候选打分 | 固定 |
| 历史回放池 | 保存已发现的结果与关系 | 随在线搜索不断扩展 |

这个拆分避免两种误读：它没有因为标题包含 RSI 就自动重新训练模型；它也不只是存一份反思笔记，而是修改会影响后续发现过程的可执行策略。[官方 README](https://github.com/google-research/dream-rsi)

## 3. 一个发现树例子

下图完全是教学数据：

```text
初始程序 r
├─ 分支 A
│  └─ A1: 0.10 → A2: 0.15 → A3: 0.95
├─ 分支 B
│  └─ B1: 0.40 → B2: 0.45 → B3: 0.46
└─ 分支 C
   └─ C1: 0.20 → C2: 0.60 → C3: 0.65
```

如果策略只根据当前最高分继续投入，可能反复追 B，错过 A 后面的突破。若平均分配所有预算，又可能在明显停滞后仍浪费调用。探索策略研究的是这些取舍。

在线时，A3 的结果并不预先存在；发现 Agent 可能生成好程序，也可能失败。历史树则记录某一次已经发生的结果，回放时读取这些结果。

**存储端拥有完整历史，不表示策略在决策时可以看见所有未来分数。** 这是回放实验有效性的基本条件。

## 4. 共享决策接口：让同一策略在线与离线工作

论文让探索策略通过共同的决策接口选择要继续的节点或批次。在线接口触发真实生成和评测；回放接口返回历史中对应的已记录延续。[方法 §3](https://arxiv.org/html/2609.14858v2#S3)

```text
探索策略 π
  ├─ 在线环境：选择节点 → 调用发现 Agent → 运行评测器 → 新结果
  └─ 回放环境：选择节点 → 揭示已记录子节点 → 已有结果
```

论文的分支内部按记录的父子顺序推进，根节点可用于打开新分支。回放不凭空产生历史树外的程序，也不构成一个能预测任意代码执行结果的通用世界模型。

### 4.1 为什么接口一致很重要

若离线策略可以读取真实环境拿不到的信息，它会在回放中“作弊”；若在线与离线动作定义不同，离线优化出的代码也可能无法部署。

因此应该统一：可见状态、合法动作、预算消耗、批次完成语义、终止条件和异常处理。类名相同还不够，需要具体行为一致。

## 5. 完整闭环：在线扩展世界，离线改写策略

### 5.1 Online rollout

当前策略按观察选择分支和并行批次，发现 Agent 生成候选，评测器验证并评分，形成新树。结束后把整棵树加入历史池。

### 5.2 Offline dreaming

策略开发 Agent 阅读已有策略及回放反馈，修改策略代码。各候选在累积的回放世界上、不同预算偏好下执行，得到质量与成本结果。

### 5.3 Selection and deployment

将候选与当前策略一起比较，选得分最高者用于下一轮在线搜索。在线世界继续变化，下一次离线评估也随历史增加而改变。[公开实现](https://github.com/google-research/dream-rsi)

```text
πt → 在线发现 → 新历史树 Tt
                  ↓
               历史池 Ht
                  ↓
         策略代码改写与多预算回放
                  ↓
             选出 πt+1
                  ↓
             下一轮在线发现
```

### 5.4 和普通轨迹记忆的区别

普通经验复用往往是把“上次怎样做”放入上下文；这里进一步把历史结构变成可执行评测环境，使多个探索策略可以在相同历史上比较。这是方法上最值得学习的部分。

## 6. 质量与成本：为什么只看最高分不够

策略 X 用 100 次调用找到 0.95，策略 Y 用 10 次调用找到 0.90，哪个更好？答案取决于预算和目标。论文通过多个预算偏好得到一组质量—成本点，再用 Pareto 前沿组织比较。

对一个回放世界：

- `B`：历史中已评估的非根节点数。
- `S`：该世界历史最好分数，要求可用于归一化。
- `n`：某次回放消耗的发现调用数。
- `s`：回放实际揭示的最好分数。
- `a = clip(s / S, 0, 1)`：相对该历史世界上限的质量。

这里的 1 表示达到这棵历史树已知的最好结果，不是解决任务的绝对最优。[论文目标定义](https://arxiv.org/html/2609.14858v2#S3)

### 6.1 支配关系

若一个方案更便宜且质量不低，另一个点就被支配。只保留非支配点，可以得到不同预算下有意义的权衡，而不是用一个固定成本系数掩盖全部变化。

### 6.2 归一化超体积

按成本递增排列前沿点 `(n_j, a_j)`，令 `a_0=0`，质量成本部分可写成：

```text
HV = Σ_j [(a_j - a_(j-1)) × (B - n_j)] / B
```

直观上，越早达到较高质量，覆盖的有效面积越大。只有耗尽历史全部调用才达到最好分，通常不能在这个指标上体现节省。

### 6.3 手算一个例子

设 `B=10`，前沿点为 `(2, 0.6)` 与 `(5, 1.0)`：

```text
HV = [0.6 × (10-2) + (1.0-0.6) × (10-5)] / 10
   = (4.8 + 2.0) / 10
   = 0.68
```

若另一个策略必须花满 10 次才达到 1.0，它的对应面积可能很小甚至为零。这个评价偏好在有限预算下尽早发现好结果。

### 6.4 并行惩罚

论文目标还减去一个与顺序决策轮数 / 调用数相关的项。若同样 8 次调用分成两个并行批次，顺序轮数比串行执行低，因此更受偏好。

但这是并行效率代理，不是真实墙钟时间保证。调用时长、尾部任务、GPU 排队与工具瓶颈会影响实际耗时，部署实验仍要测墙钟时间。

## 7. 一个独立教学函数：算 Pareto 超体积

以下代码是本文为上面的数学例子写的教学函数，不是从项目复制的实现，也不包含策略执行、回放和并行惩罚：

```python
def quality_cost_area(points, budget):
    if budget <= 0:
        raise ValueError("budget must be positive")
    for cost, quality in points:
        if not (0 <= cost <= budget and 0 <= quality <= 1):
            raise ValueError("point outside the example domain")

    best_quality = 0.0
    area = 0.0
    for cost, quality in sorted(points, key=lambda p: (p[0], -p[1])):
        if quality > best_quality:
            area += (quality - best_quality) * (budget - cost)
            best_quality = quality
    return area / budget


print(quality_cost_area([(2, 0.6), (5, 1.0)], 10))  # 0.68
```

可以自行加入被支配点 `(7, 0.8)`，观察面积是否保持不变；再把第一个点成本从 2 改为 4，观察“更晚得到相同质量”如何影响分数。

## 8. “新策略不比旧策略差”的严格范围

论文保留当前策略作为候选，因此在**同一历史池、同一确定性回放目标、相同评测设置**上，选择的最佳分数不低于当前策略。这是选择规则带来的有限保证。

它不能推出：

- 下一轮在线任务表现一定更好；
- 新增历史后，旧分数仍然保持不变；
- 所有未见任务都能迁移；
- 真实总成本和风险一定下降。

原因是回放世界有覆盖边界，在线生成是随机的，新的策略会改变接下来遇到的状态分布。这里没有对任意未知环境的单调改进定理。[选择规则](https://arxiv.org/html/2609.14858v2#S3)

## 9. 论文实验应该怎样读

v2 报告 9 个任务、4 个领域，包括算法工程、数学优化、GPU kernel 与 harness 优化。科学发现任务的重要对照是 Recursive Fixed Exploration：两组使用相同基础发现 Agent、评测器、起点和每轮预算，而对照不改探索策略。[实验 §4](https://arxiv.org/html/2609.14858v2#S4)

作者在特定 kernel 任务上报告：达到相似性能需要更少 generation，或在近似预算下获得更好的执行性能。**generation 数量的节省，不能直接改写成整个系统 API 账单按同倍数下降。** 离线策略开发、评测、编译、GPU 执行与失败重试仍有成本。

一个重要限制：harness 优化部分侧重端到端结果，论文因成本原因没有提供对应的完整 fixed-policy 对照。因此这部分能展示搜索得到的 harness 有用，却不足以单独精确归因“回放式策略改进相对固定策略贡献多少”。

不要把论文不同领域的模型、指标和协议混成一个统一成绩，也不要把源码中的默认运行参数直接等同于所有论文实验配置。

## 10. 这是否算 RSI

可以分成两种说法：

- **具体、可验证的说法：** 系统用自己的发现历史，修改探索策略代码，影响下一轮发现与下一批历史。
- **更强、尚未由此证明的说法：** 系统可以无限持续、自主加速地改进所有能力，甚至不断产生更强底座模型。

前者是论文研究对象，后者不是这些实验自然推出的结论。核心实现中固定的基础 Agent、评测器和元层编排仍是能力边界。

和 Harness² 对照：

| 维度 | Dream-RSI | Harness² |
| --- | --- | --- |
| 首要改动对象 | 探索策略代码 | 执行 harness 文件与经验库 |
| 关键反馈 | 历史树回放的目标分数 | 行为对比、产物与源材料 |
| 核心环境 | 有评分器的发现任务 | 缺少标准答案反馈的新任务 |
| 跨轮积累 | 回放世界池 | 改进经验与完整 harness |
| 最需验证 | 回放到在线的迁移 | 无标签选择与跨任务经验质量 |

它们可以启发同一系统的不同层次，但不是天然兼容的同一种算法。

## 11. 六个研究风险与对应实验

| 风险 | 为什么发生 | 对应检验 |
| --- | --- | --- |
| 历史支持不足 | 新策略偏好的方向未被记录 | 新在线 rollout 检验 |
| 回放过拟合 | 反复针对同一批树修改代码 | 留出树、后续时段与新任务 |
| 未来信息泄漏 | 策略读取未揭示分数或全树文件 | 限制接口、审计读取 |
| 分支标识投机 | ID 或顺序暗含好坏信息 | 匿名化和重排敏感性测试 |
| 奖励投机 | 候选利用评分器缺陷 | 独立正确性验证与负例 |
| 成本遗漏 | 只数发现调用 | 统计元优化与评测总开销 |

这些是本文提出的复现审查要点，并不表示原项目已经逐项通过。特别是留出历史树仍不替代在线验证，它只是在有限历史上的额外检查。

### 11.1 零分与退化历史

目标归一化需要处理历史全失败、最好分为零、有效节点太少等情况。当前回放评估代码会对某些退化 trace 做跳过或无信号处理。报告时应记录被排除的比例，而不能只留下能产生漂亮曲线的世界。[eval.py](https://github.com/google-research/dream-rsi/blob/8ec35bd2538220517ce1bfca4282db21b8c518db/dream_rsi/learning/heuristic_search/eval.py)

## 12. 如何设计一个小规模复现

先选择便宜、正确性可确定验证的任务，例如小型组合优化或程序输出优化。不要一开始就运行大型 kernel 搜索。

### 12.1 固定不变的部分

问题分布、发现模型、生成提示、候选评测器、初始程序、每轮预算、最大并发和采样设置。记录策略开发模型与费用，避免把元优化资源隐藏起来。

### 12.2 对照设计

| 组别 | 作用 |
| --- | --- |
| A 固定策略 | 得到基本搜索曲线 |
| B 固定策略 + 同样历史访问 | 排除仅仅看到更多历史的收益 |
| C 人工策略调参 | 检查自动改写是否优于简单规则 |
| D 回放优化策略 | 检验方法主体 |
| E D 但限制 / 打乱历史池 | 检验历史积累和顺序敏感性 |

为每组保留多个随机种子和独立工作区。早期比较应共享同一初始发现树，但不要共享后续生成缓存和会污染结果的记忆。

### 12.3 最低报告集合

- 在线最好分随发现调用数变化的曲线。
- 达到预设阈值所需调用数及未达到比例。
- 总费用、墙钟时间、评测时长与并发。
- 回放得分与下一轮真实收益之间的关系。
- 无效候选、编译失败、评分器异常与重试。
- 策略代码 diff 和行为变化解释。

阈值应在比较前定义；不能每种方法挑一个最有利阈值再报告加速倍数。

## 13. 源码精读路线

固定快照：[Dream-RSI source](https://github.com/google-research/dream-rsi/tree/8ec35bd2538220517ce1bfca4282db21b8c518db)。

| 入口 | 关键问题 |
| --- | --- |
| `dream_rsi/orchestrate.py` | explore、learn、promote 怎样连接？ |
| `dream_rsi/policy/baseline.py` | 固定策略怎样按波次分配宽度和深度？ |
| `dream_rsi/policy/` | 可发现策略的接口与模板是什么？ |
| `dream_rsi/env/trace_env.py` | 何时揭示节点，怎样限制未来信息？ |
| `dream_rsi/learning/trace_pool.py` | 历史树如何归档与收集？ |
| `dream_rsi/learning/discover.py` | 如何改写、评估、选择策略？ |
| `dream_rsi/learning/heuristic_search/eval.py` | 预算扫描、前沿、并行惩罚与异常语义 |
| `tasks/` 与 `scripts/` | 每个任务依赖、评测器和启动配置 |

阅读时做一张“四列追踪表”：策略可见输入、合法动作、环境内部拥有但不可见的信息、真实副作用。比单纯理解一个策略函数更有助于发现实验漏洞。

## 14. 上手与复现环境

公开 README 要求 Python 3.10+；论文任务的部分数据需要另行获取，数学、算法与 GPU kernel 的依赖不同。下面是基于 README 的小运行路径，命令未在本文环境执行。[安装与启动](https://github.com/google-research/dream-rsi#installation)

```bash
git clone https://github.com/google-research/dream-rsi.git
cd dream-rsi
git checkout 8ec35bd2538220517ce1bfca4282db21b8c518db
pip install -e '.[tasks]'
bash scripts/fetch_tasks.sh

# 先检查任务文件、模型配置、执行器与依赖，不发起搜索。
DRY_RUN=1 bash scripts/run_dream_rsi.sh circle_packing_26

# 配置有效模型凭据及执行器后，才运行一个较小搜索。
WORKSPACE=workspace/smoke ROUNDS=2 BRANCHES=3 REFINE=1 MAX_WORKERS=3 \
  bash scripts/run_dream_rsi.sh circle_packing_26
```

Windows 可使用 WSL 或 Linux 环境。实际运行前应核对当前 agent CLI 与论文版本的兼容性，不把历史模型 ID 当成永久可用承诺。GPU 性能评测要避免其他任务争用同一设备。

论文 v2 的覆盖范围与仓库可直接启动的任务也应逐项核对，不能看到论文有四个领域，就假定所有复现脚本已经完整公开。

## 15. 为 harness 工程迁移时要改什么

如果希望用 Dream-RSI 思想优化研究 Agent，可以让探索策略决定：下一轮试哪种上下文管理方案，在哪类失败任务上继续测试，如何分配候选 budget。

但不能直接把历史成功率表当成任意 harness 的精确 simulator。新工具、新 prompt 和新上下文可能改变未来轨迹，历史中没有其真实结果。

一个务实的迁移方案是：先把回放作为廉价候选筛选，再用真实任务验证；通过留出任务与总预算对照决定是否部署。公开代码没有自动替你完成这个业务迁移，本文也不把它描述成已经实现的集成。
