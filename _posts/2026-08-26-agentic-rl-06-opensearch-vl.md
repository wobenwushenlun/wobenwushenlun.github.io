这一轮学习的最后一站是 [OpenSearch-VL](https://arxiv.org/pdf/2605.05185)。我重点追了两个部分：训练数据怎样构造，以及一个多模态搜索 Agent 到底应该怎样评测。

## 为什么普通 VQA 数据不够

如果图片本身已经包含答案，模型只靠视觉识别就能解决问题，搜索工具就变成了可有可无的装饰。

要训练真正的多模态搜索 Agent，数据必须迫使模型跨越多个信息源。例如：

```text
识别图片中的实体
→ 根据实体搜索网页
→ 从结果中找到第二个线索
→ 再搜索或交叉验证
→ 汇总成最终答案
```

因此数据构造的重点不是普通问答数量，而是确保题目具有外部知识依赖和多跳搜索必要性。

## 我理解的数据管线

OpenSearch-VL 的数据思路可以抽象为：

```text
从知识源和图片建立实体锚点
→ 生成需要跨模态、多跳检索的问题
→ 改写实体和问题表达，降低模板痕迹
→ 分阶段过滤过易、不可答或证据不足的问题
→ 用更强模型生成工具使用轨迹
→ 检查最终答案和搜索过程质量
→ 分别形成 SFT 与 RL 数据
```

这里每个过滤器都在改变最终训练分布。只报告“过滤后剩多少条”还不够，还应该问：哪些类型的问题被过滤掉了？是否把最困难但最有价值的数据一起删掉了？

## Source anchor 与模糊实体改写

构造题目时，如果答案和证据没有牢固绑定到源页面，就容易生成表面合理、实际无法验证的问题。source anchor 的作用是保留问题—实体—证据之间的落点。

但问题如果直接复用页面标题或标准实体名，检索又会过于简单。模糊实体改写通过别名、描述或间接线索降低字符串匹配，让模型必须结合视觉内容和搜索结果定位对象。

这两者形成一个张力：

> 题目既要有可验证的证据，又不能简单到复制关键词就能命中答案。

## 训练奖励与最终评测不是一回事

我最初容易把论文中的“奖励体系”和“Benchmark 指标”混在一起。实际上它们服务于不同目的。

训练阶段可以同时评价：

- 输出格式是否可解析；
- 最终答案是否正确；
- 搜索查询是否合理；
- 过程是否找到有效证据；
- 是否出现致命工具错误。

而论文最终排名往往更接近：在多个 Benchmark 上执行一次 Agent，使用语义 Judge 判断最终答案对错，再汇总 Pass@1 或平均准确率。

这意味着训练时关心“过程 + 结果”，最终主指标却可能主要关心“结果”。

## Direct、RAG 与 Agentic 的三层对照

一个比较有意义的评测结构是：

```text
Direct：只看图片和问题，直接回答
RAG：系统预先检索一次，再回答
Agentic：模型自主决定何时、搜什么、搜几轮
```

这种分组能检验自主工具使用是否真正带来增益。但要注意，不同 Agent 可能使用不同搜索后端、提示词和工具预算，因此结果并不天然公平。

## 只看最终正确率还缺什么

一个 Agent 搜索三十次后偶然答对，与搜索两次并给出可靠证据的 Agent，在最终准确率上可能完全一样。若要评价可用性，我认为至少还需要：

```text
平均工具调用次数
搜索成功率与无效查询比例
引用或证据支持率
平均 token 与 API 成本
端到端延迟
工具格式错误率
fatal rate
相同任务的多次运行方差
```

在线搜索环境还会随时间漂移，Judge 本身也可能产生波动。因此最终分数应被理解为：

```text
模型策略能力
+ 搜索后端状态
+ 网页可访问性
+ 工具预算
+ 评价模型偏差
```

## 这轮学习最终留下的框架

回看整个过程，我现在会用六个问题分析一项 Agentic RL 工作：

1. Agent 可以观察什么、执行什么动作？
2. 一条 episode 怎样被表示和保存？
3. 最终 reward 怎样分配到步骤或 token？
4. 环境内容和模型动作怎样正确 mask？
5. 优势估计与 loss 聚合是否引入偏置？
6. 评测是在测任务成功，还是也测效率、证据和成本？

从 Search-R1 到 OpenSearch-VL，我最大的变化是：不再把 Agentic RL 看成“给 Agent 套一个 GRPO”，而是把它看成环境、数据、奖励、优化和评测共同构成的闭环。

这套理解还很初步，后续我打算继续追两个方向：一个是亲手跑通最小可复现训练，另一个是为搜索 Agent 设计更完整的过程评测。
