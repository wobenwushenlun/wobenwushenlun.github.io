第 8 章区分了生成、批评和验证。很自然会想到：能不能让不同 Agent 分别承担这些工作？

可以，但新增角色也会新增通信、协调、预算和一致性问题。本章要回答：**哪些工作值得拆开，传递什么信息，谁拥有最终决策权，遇到矛盾时怎么办？**

建议用时 5 小时：概念与资料 60 分钟、协议实现 90 分钟、异常与协作实验 90 分钟、迁移和复述 60 分钟。

## 9.1 多个角色不自动构成多个 Agent

先区分四种常见结构：

| 结构 | 实际发生了什么 | 典型限制 |
| --- | --- | --- |
| 一次提示写三个角色 | 一个调用生成三段文本 | 仍共享一次上下文和生成过程 |
| 三步固定模型链 | 三次调用分别读、写、评 | 流程由程序预设，不一定各自自主行动 |
| 多个 Agent | 各有上下文、工具和局部行动循环 | 需要交接、权限、预算与状态协调 |
| 多个并发任务 | 多份工作在时间上重叠 | 可能只是普通函数，并不一定含 LLM |

所以“开了三个线程”和“创建了三个角色 Prompt”都不足以说明你实现了完整多 Agent 系统。要看每个参与者能决定什么、持有什么状态、执行哪些工具，以及如何协作。

AutoGen 论文讨论了通过多个可交互 Agent 的对话来组织任务执行；它提供的是一种协作框架思路。学习本章无需安装该框架，也不把其历史版本 API 当成今天的调用说明。[AutoGen 原论文](https://arxiv.org/abs/2308.08155)

## 9.2 拆分的收益要抵得过协调成本

适合拆分的例子是：规格调查、某个独立模块的实现分析、测试约束核对。它们能在清晰输入下各自获得证据，然后按约定交付结果。

不适合随意拆分的情况包括：两个角色同时修改同一个函数、每一步都依赖另一角色刚产生的状态、任务小到单次调用已经足够。

Anthropic 的多 Agent 研究系统文章介绍了协调者与子 Agent 的设计、任务边界以及上下文和成本方面的工程考虑。那是研究型工作负载的经验，不应把其效果和资源比例直接移植到代码修复任务。[多 Agent 研究系统工程报告](https://www.anthropic.com/engineering/multi-agent-research-system)

本课的判断方式是：先给一个强单 Agent 基线，再看拆分是否带来新证据、隔离干扰或缩短关键路径。不能只因为输出更长、对话更多就认为效果更好。

## 9.3 从协调者与工作者开始

本章采用中心协调结构：

```text
                       Coordinator
                 任务、版本、预算与收集
                   /       |       \
          Spec Reader     Coder    Reviewer
              |             |        |
            规格报告       候选报告   约束报告
                   \       |       /
                协调者校验、解决缺口
                         |
                 独立 Verifier
                         |
                 接受提议或继续调查
```

相比角色之间任意互发消息，这种结构更容易跟踪任务状态。代价是协调者可能成为瓶颈，也可能在汇总时遗漏重要细节。

其他结构包括链式交接、共享黑板、点对点讨论和辩论。学习顺序上先掌握中心协调，再根据确实出现的瓶颈扩展，而不是一次引入所有通信方式。

## 9.4 角色的职责与输入要一起设计

真实 Coding Agent 可以按下面的方式分工：

| 角色 | 负责产物 | 必要输入 | 不拥有的权限 |
| --- | --- | --- | --- |
| Planner / Coordinator | 子任务契约、预算与最终整合 | 用户目标、验收标准、各角色状态 | 不能伪造工具执行结果 |
| Spec Reader | 规格、范围与矛盾项 | 业务文档及来源版本 | 不能因旧经验改写规格 |
| Coder | 候选修改与影响范围 | 当前代码、相关规格、依赖约束 | 不能自行放宽最终测试标准 |
| Reviewer | 具体缺陷、证据与未验证项 | 候选、规格、相关代码和测试 | 审查意见不等于测试通过 |
| Verifier | 可重复的检查结果 | 冻结候选与固定验收集 | 不根据语言说服力改变分数 |

共享所有历史最省设计时间，但会重复消耗上下文，还可能让所有角色继承同一错误。完全不共享则可能丢掉必要约定。

合理的交接单位是“完成这个子任务所需的最小信息”，包括目标、范围、输入产物版本、可用工具、停止条件和需要返回的字段。

## 9.5 消息应是可检查的协议

教学报告类型：

```python
@dataclass(frozen=True)
class Report:
    task_id: str
    revision: int
    role: str
    evidence: dict[str, str]
    candidate: str
```

本课 `evidence` 保存文件名到内容哈希的映射，`candidate` 是第 8 章可信候选表里的 ID。真实系统应进一步包含证据行范围、理由摘要、失败状态、已使用预算和未验证项。

为什么需要任务 ID 和修订号？因为慢任务可能在协调者已改变计划后才返回。若直接接受旧报告，旧候选可能覆盖新版本分析。

为什么还要校验发送者？报告里写了 `role=reviewer` 不代表它真来自 Reviewer。示例由宿主给 `submit(sender, report)` 提供发送者身份并与内容核对；这不是密码学认证，但能演示“身份来自通道，不只来自自报字段”。

生产系统若通过网络通信，还需要认证、访问控制、序列化校验与重放策略。本课使用同一 Python 进程内的可信类型，尚未实现这些服务能力。

## 9.6 证据隔离与最终整合

代码：[ch09_multi_agent.py](/assets/learning/llm-agent/ch09_multi_agent.py)。它依赖 `ch03_tools.py`、`ch07_memory.py`、`ch08_reflection.py` 及第 7 章的传递依赖 `ch06_context.py`，统一下载整套实验最方便。

三个角色分别得到 README、实现、测试文件的副本，程序输出各输入包的来源名称和字符数。这样可以检查角色拿到了哪些数据。

**这是顺序执行的角色协议模拟器，没有启动真实 LLM Agent，也没有并发执行。** 每个角色的候选答案由脚本预设，并非阅读其局部输入后推理得出。

特别要注意：真实 Coder 如果只看到实现而没有业务定义，不足以确定正确折扣语义；真实 Reviewer 也通常需要候选及规格。示例的局部输入仅用于检验范围与协议，接真实模型时必须补齐这些依赖，不能照抄后声称信息充分。

独立上下文也不等于操作系统隔离。此处所有函数同进程执行，权限限制来自宿主提供的数据与工具；没有容器级安全边界。

## 9.7 协调者接受报告之前检查什么

```text
检查剩余消息预算
  → 检查 task_id 和 revision
  → 检查实际 sender 与报告 role
  → 拒绝已接收角色的重复提交
  → 检查候选 ID 与角色可引用来源
  → 比较证据版本
  → 保存报告副本
```

拒绝的提交也会消耗消息预算。否则一个出错角色可以不断提交无效报告，绕过总量限制。

重复消息不能被当成第二票。示例收到同一角色的第二份报告直接拒绝；真实系统如果要支持重试幂等，可以给消息增加 ID，并对同 ID 同内容返回之前的处理结果，而不是再次触发副作用。

示例只核对报告引用的版本是否等于协调者启动时的文件快照，不会在汇总前再次读取磁盘。文件可能并发变化的系统还要校验当前版本，或在不可变工作树中执行任务。

## 9.8 正常路径：一致意见仍需验证

```powershell
python -B assets/learning/llm-agent/ch09_multi_agent.py
```

三个脚本角色都建议 `payable`，报告均被接受。协调者确认完整、无矛盾后，使用第 8 章公开算术检查独立验证候选。

预期状态是 `verified_proposal`，并明确 `files_modified=false`。含义是“固定候选通过了当前公开算术检查”，不是已提交补丁，也不是所有真实输入都正确。

再运行：

```powershell
python -B assets/learning/llm-agent/ch09_multi_agent.py --scenario unanimous_wrong
```

这时三个角色一致建议 `saved_amount`。协调者不因三票一致就接受，而是得到 `verification_failed`。

这个例子解释了相关错误：相同模型、相同材料或相同起始假设可能让多个角色一起犯错。多数票的数量不是独立证据数量。

## 9.9 不一致、缺席与旧证据

### 场景 A：角色意见冲突

```powershell
python -B assets/learning/llm-agent/ch09_multi_agent.py --scenario conflict
```

两份报告建议 `payable`，一份建议 `saved_amount`。系统返回 `needs_resolution`，列出不同候选，不直接按 2:1 接受。

这是一种保守教学策略，不表示所有系统必须一票否决。真实协调者可以追加查证、根据业务规格解决分歧，或让独立验证器检查多个候选；每种策略都需要额外预算和明确停止条件。

### 场景 B：报告来自旧版本

```powershell
python -B assets/learning/llm-agent/ch09_multi_agent.py --scenario stale
```

Coder 的证据哈希被模拟为旧值，应收到 `stale_evidence`，最终为 `incomplete`。不能因为提议碰巧正确就忽略其来源已经不匹配。

### 场景 C：关键角色没有交付

```powershell
python -B assets/learning/llm-agent/ch09_multi_agent.py --scenario missing
python -B assets/learning/llm-agent/ch09_multi_agent.py --max-messages 2
```

前者跳过 Reviewer，后者不足以接收三份报告。两者都不宣称完整验收。报告列出缺少的角色，便于决定重试、降级或交还用户。

本模拟器没有真实等待，因此没有实现网络超时和取消。迁移到并发调用时要增加截止时间、失败收集和取消传播，不能只是把循环换成并发库。

## 9.10 并行化不等于成本下降

若任务独立，理想并行耗时近似由最慢分支加汇总开销决定；但总模型用量通常需要累加所有分支。共享上下文重复发送、失败重试和审查都会增加成本。

实验时至少记录：

```text
任务级成功率
总输入、输出及工具用量
端到端耗时与各分支耗时
失败、重试、被拒绝消息数
冲突次数与最终解决方式
被重复收集或遗漏的关键证据
```

每个角色分配 1000 Token，不等于整个系统只花 1000 Token；每个子 Agent 最多六步，也不等于总共最多六步。

本章只实现共享的消息数量预算。它不限制未来真实模型的 Token、网络时间或子循环步数；这些指标需要宿主逐一核算。

## 9.11 怎样设计单 Agent 对照

本课不通过离线预设角色得出“多 Agent 更强”的结论。接入真实模型后，建议至少设置：

| 组别 | 结构 | 用途 |
| --- | --- | --- |
| 单 Agent | 可访问同样证据与工具 | 基础基线 |
| 单 Agent 多次独立尝试 | 相同总预算下产生多个候选 | 区分更多采样带来的收益 |
| 多角色固定链 | 同一模型按固定步骤交接 | 区分角色提示与自主调度 |
| 多 Agent 协作 | 独立循环、约定交接与协调者 | 测试真正的分工收益 |

使用同一任务集、相同外部验收、可比的总预算，报告延迟与成本。若系统采用不同模型，也应明确模型能力是额外变量。

对代码修改任务，还必须明确写入所有权。可以每个工作者独立分支或工作树生成补丁，由协调者统一整合；不要让多个角色同时覆盖一个共享文件，然后靠最后写入者决定结果。

本章只提议可信候选，不写文件，完整代码执行和分支整合留到后续章节。

## 9.12 迁移作业、自测与阅读

迁移作业：为报告增加 `message_id` 和明确的成功/失败状态。设计幂等重试：同 ID 同内容不重复计票，同 ID 不同内容拒绝。然后模拟一个在任务修订后才返回的旧报告，确认它不能覆盖新结果。

第二阶段再把脚本角色换成模型。先给 Coder 增加经过验证的规格交接，给 Reviewer 提供冻结候选与规格；保留第 8 章的外部验证器，不让 Reviewer 通过改字段决定测试成功。

闭卷回答：

1. 三个角色标签、三个模型调用和三个 Agent 有何不同？
2. 为什么发送者不能只从消息中的 `role` 判断？
3. 三个角色意见一致，为什么仍可能全部错误？
4. 为什么并行更快不一定更便宜？
5. 两个 Agent 修改同一文件时，应先定义什么？

给 Claude Code：

```text
请检查我的协作协议是否允许重复报告变成多票，
旧版本结果覆盖新结果，或 Reviewer 自封测试通过。
给出一条具体事件序列，不要只建议增加一个新的 Agent。
```

## 9.13 第 7～9 章的项目关系

```text
第 6 章：选择当前证据
    ↓
第 7 章：保存带范围和版本的经验，检索前检查有效性
    ↓
第 8 章：以外部反馈约束修订，把失败解释当成候选经验
    ↓
第 9 章：分配角色、传递带版本的报告、协调冲突并独立验收
```

配套文件目前是三个可独立验证的实验模块；第 9 章复用了哈希与验证器，但没有把真实模型、数据库记忆和多角色网络调度整合成生产系统。这个界限也是你应在实验报告中保留的部分。

- 本章变化：增加了角色契约、消息接收规则、版本检查与协作失败状态。
- 可信度：离线协议行为可验证；论文与工程报告提供设计依据，未在本课测得真实多 Agent 收益。
- 当前缺口：如何以标准协议连接更多工具，以及如何把重复工作打包为可复用能力。
- 掌握状态：待幂等与过期消息迁移作业，以及真实模型条件下的对照。
