前两章加入了行动循环和任务图，Agent 会逐渐积累 README、函数、测试、搜索结果和失败记录。新的问题是：**下一次调用模型时，要把哪些信息放进去？**

本章把上下文选择做成独立组件，而不是在提示词后面无限拼接日志。目标是让你知道一次判断依据哪些证据、为什么这些证据被选中、什么被舍弃，以及证据是否仍对应当前文件。

建议用时 4 小时：概念与资料 45 分钟、实现 60 分钟、预算与检索实验 90 分钟、自测和迁移练习 45 分钟。

## 6.1 上下文工程解决什么问题

提示词说明“你要怎样工作”，上下文还包括任务、对话历史、工具定义、文件片段、执行记录等信息。上下文工程关注这些信息怎样选择、组织和持续更新。

Anthropic 的相关工程文章讨论了有限上下文下的信息选择、按需获取和长任务压缩等方法。可以把它作为设计思路，不把某一种压缩比例或窗口利用率当成通用最优值。[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

对我们自己的代码助手，至少有三种失败需要分清：

- **没找着**：相关文件从未进入候选集合。
- **找到了但没放进去**：被预算、排序或截断丢掉。
- **放进去了但没用好**：模型误解、忽略或误用了证据。

这三个问题分别需要改检索、改组装、或改决策与验证。单纯扩大窗口可能掩盖原因，却不一定解决它。

## 6.2 先区分存储与当前输入

```text
代码仓库、完整历史、工具日志
            ↓ 检索候选
            ↓ 排序与取舍
本轮模型实际收到的上下文
            ↓ 模型决策
新的行动与观察 → 更新存储与候选
```

完整历史可以存在磁盘，不意味着每轮都要全部发送。反过来，一个重要约束即使存过，如果没有通过适当方式进入本轮输入，模型也不一定会遵守它。

第 7 章的记忆关注什么值得跨任务保存、如何检索与更新；本章关注本次调用的工作集。检索可以是上下文工程的一部分，但上下文工程不等于向量数据库。

对代码仓库，函数名、文件名、错误信息往往是很好的检索线索。先用词法搜索得到可解释基线，再判断是否需要语义检索。

## 6.3 一次调用怎样分配预算

用下面的预算表思考，而不是把所有空间分给文件：

| 部分 | 例子 | 处理方式 |
| --- | --- | --- |
| 稳定规则 | 任务边界、输出要求、授权约束 | 独立保留，避免被普通内容挤掉 |
| 用户目标 | 本次问题与验收条件 | 每轮保证语义完整 |
| 工具定义 | 名称、参数、用途 | 只暴露当前需要的工具集合 |
| 必要历史 | 最近动作、失败信息、待完成步骤 | 保持协议完整再压缩 |
| 外部证据 | 文件内容、搜索片段 | 检索、排序、分块和裁剪 |
| 输出空间 | 允许模型产生的响应 | 提前预留，遵守具体模型限制 |

概念上可以写成：

```text
可用证据预算 = 总容量 − 固定输入 − 必要历史 − 输出预留
```

真实 API 的限制与计量要以所选模型为准。这个减法只是容量规划，不能代替服务端计数，也不能保证所有模型都以相同方式计算输入、思考与输出。

本章离线示例使用 Python `len()` 计算 Unicode 字符数，明确叫 `evidence_budget`，只约束渲染后的证据文本。它**不是 Token 数，不是总请求长度，也不是费用上限**。

在线应用可以使用官方 Token counting 接口，对准备好的系统提示、消息及工具定义进行计数。计数结果仍应与真实响应用量对照，而不是用字符除以某个常数冒充精确 Token。[Token counting 文档](https://platform.claude.com/docs/en/build-with-claude/token-counting)

## 6.4 从仓库地图到片段候选

面对陌生项目，先看低成本的地图：允许访问的文件、目录结构、入口、语言和已知测试位置。地图用于导航，不等于源文件的完整证据。

本课仍只访问第三章允许的三个教学文件；没有递归扫描个人目录，也没有扩展文件权限。用相同的小仓库，可以把注意力放在选择算法上。

手动检索时可在教学目录使用：

```powershell
rg -n -F 'final_price' assets/learning/llm-agent/fixtures
rg -n -F 'discount' assets/learning/llm-agent/fixtures
```

查询来自问题中的实体与符号。比如中文问题“为什么折后价格不对”，可以先提取实际函数名 `final_price`，再用它查代码。直接把中文长句当作英文代码中的精确关键词，可能什么也找不到。

没有相关命中时，应改写查询、沿引用寻找定义或承认缺口。不要把空检索结果解释成“仓库没有 Bug”。

## 6.5 分块必须保留来源

本课将文件每四行分成一个片段，每个片段携带：

```python
@dataclass(frozen=True)
class Chunk:
    path: str
    start: int
    end: int
    digest: str
    text: str
```

`start/end` 是从 1 开始、包含两端的行号。`digest` 是整个文件文本的 SHA-256，用于识别这段证据来自哪一版文件。

固定四行便于演示，却可能把函数签名、实现和断言切开。真实代码通常更适合按函数、类或语法树组织片段，并把必要的 import、类型和调用上下文附上。

片段不能只剩一段裸文本。否则模型指出“这一行有问题”时，你无法定位原文，也无法判断它引用的是不是早先已修改的版本。

本课记录的行号与哈希针对通过 UTF-8 解码后的文件文本快照；读取所有文件并不是事务性快照。学习环境假设没有其他程序同时修改这些教学文件。

## 6.6 实现一个可解释的 ContextBuilder

代码：[ch06_context.py](/assets/learning/llm-agent/ch06_context.py)，复用 [ch03_tools.py](/assets/learning/llm-agent/ch03_tools.py) 的受限文件读取。

示例的排序分数非常简单：

```text
score(chunk, query)
    = 查询词集合与“文件路径 + 片段内容”词集合的交集大小
```

它把英文单词、数字、Python 标识符中的组成部分转成小写集合。比如 `final_price` 拆成 `final` 与 `price`。它不是 BM25、Embedding 或中文分词器，也不利用词频。

随后执行：

```text
按分数从高到低排序；同分按文件名和起始行稳定排序
逐个候选：
    没有查询词命中 → 标记 no_term_overlap
    加上来源标签后超过剩余字符预算 → 标记 budget
    否则 → 加入本轮证据
输出：选中片段、被舍弃片段及原因、最终证据文本
```

预算包含来源标签、哈希与换行。只计算正文而忽略包装文本，会造成“看起来没超预算，实际组装后却超了”的错误。

某个大块装不下时，程序继续考虑后面的小块。它没有解最优背包问题，也没有按语义合并相邻块。优点是每次决定可以检查；缺点是可能保留很多低价值短块，而错过重要长块。

这个基线的目的不是赢过所有检索方法，而是让每一个缺失证据都有可追查的原因。

## 6.7 先观察默认运行

```powershell
python -B assets/learning/llm-agent/ch06_context.py
```

默认查询是 `discount final_price expected 80`，证据预算 1100 个字符。输出包含：

- `context`：真正会被送入下一轮的证据文本。
- `selected`：路径、行号、分数和版本哈希。
- `dropped`：哪些片段没选中以及原因。
- `used`：与 `len(context)` 相同的字符数。

在当前教学文件上，默认选择能包含价格约定、实现和测试断言的相关片段。具体字符数依赖文件内容；练习中修改文件后，不应再机械要求数字与原示例相同。

想把它接回第 4 章，先以这些片段替换 `provided` 模式的完整文件输入；保留原来的完整输入基线。此时需要相应修改评分器的证据粒度：从“完整读过文件”改成“哪些行确实出现在选中证据中”。不能偷偷沿用有偏的判定。

## 6.8 压缩不是随便删历史

对消息历史做摘要时，要保留能影响后续动作的信息：目标、硬约束、已完成任务、未解决问题、失败类别、证据来源和文件版本。

一种简短工作摘要可以是：

```text
目标：解释折扣金额，不改文件。
已知：README 定义 0.2 为减去 20%；pricing.py 返回 price * discount。
证据：对应文件路径、行号与内容版本。
未验证：未执行测试；尚未检查其他调用方。
下一步：判断是否需要读取测试约定。
```

这个摘要是派生数据，也可能漏掉条件。模型生成的摘要不自动比原始工具结果更可信；重要约束应由程序保留，关键结论应能回到原文。

对工具消息尤其要小心：不能删除 assistant 的调用块却保留孤立结果，也不能丢掉待处理调用的一半。压缩应发生在完整工具往返之后，并维持目标接口要求的消息结构。

本章代码只组装文件证据，没有实现聊天历史自动压缩。它也不把 `[untrusted]` 文本标签当作安全边界：标签帮助区分来源，权限仍靠执行器实施。

## 6.9 文件变了，旧证据还能用吗

运行：

```powershell
python -B assets/learning/llm-agent/ch06_context.py --stale-demo
```

程序在内存副本里给 `pricing.py` 增加一条注释，不修改磁盘文件。再把选中证据的哈希与新版本比较，输出 `stale_paths_after_simulated_edit`。

如果默认选中集合包含 `pricing.py`，应检测到它已变化。若你把预算降得太低导致它未被选中，检查列表可能为空；这只代表没有“已选证据的过期项”，不能证明仓库没有任何变化。

检测出变化后，合理流程是重新读取、重新分块和重选证据，必要时重新检查基于旧内容得出的结论。不能只更新哈希却保留旧文本，那等于给旧证据贴了新版本标签。

哈希也不是事实真假的证明：它能帮助识别内容变化，不能证明这段代码语义正确或不会含有恶意指令。

## 6.10 四组实验，定位信息究竟丢在哪里

### 实验 A：预算扫描

```powershell
python -B assets/learning/llm-agent/ch06_context.py --budget-chars 300
python -B assets/learning/llm-agent/ch06_context.py --budget-chars 1100
python -B assets/learning/llm-agent/ch06_context.py --budget-chars 3000
```

不要只看 `used`。逐组确认业务定义、公式、测试断言是否仍在输入中。小预算可能只容纳一条关键事实，较大预算也不保证一定提高真实模型答案质量。

### 实验 B：查询变化

比较 `discount final_price expected 80`、`coupon` 与纯中文“折扣价格”。示例分词规则主要适用于英文代码，后两者可能没有相关命中。

这不是模型不聪明，而是检索器没有语义翻译与中文分词。先修改查询或检索器，再评价模型。

### 实验 C：分块边界

在学习副本中将 `lines_per_chunk` 从 4 改成 2 或 8，保持字符预算相同。比较来源标签占比、上下文完整性、是否把断言与测试函数切开。

分块越小并非越精确：若丢了定义条件，即便留下出错那一行也可能误诊。

### 实验 D：信息消融

保留完整证据基线，然后在相同任务上分别移除规格、实现或测试片段。若使用真实模型，记录原始回答和用量，检查它会承认缺口还是编造内容。

这能回答“哪些证据对这道题必要”，不能直接得出所有代码任务都需要相同文件的结论。

## 6.11 指标与失败分析

| 指标 | 测量方式 | 能说明什么 |
| --- | --- | --- |
| 必要证据覆盖率 | 人工预先标注的必要片段中，选入多少 | 检索和组装是否遗漏关键证据 |
| 预算使用率 | 实际证据字符数 / 字符预算 | 包装开销与容量使用情况 |
| 来源可追溯性 | 每块是否有路径、行号与版本 | 能否回查依据 |
| 过期证据数 | 选中版本与当前版本比较 | 是否在用旧代码作判断 |
| 最终任务质量 | 独立验收标准 + 原始轨迹检查 | 证据选择有没有真正帮助任务 |

预算填满不是目标：相关材料只有 500 字符时，不需要填充 5000 字符的噪声。覆盖率也要提前定义必要证据，不能在看到 Agent 结果之后随意改变标准。

运行课程测试：

```powershell
python -B -m unittest discover -s assets/learning/llm-agent -p "test_*.py" -v
```

这条命令在当前布局下收集实验目录中的单元测试；`fixtures` 没有作为测试包递归导入。不要另外运行 `fixtures/test_pricing.py` 后把教学 Bug 的预期失败误认作框架回归。

## 6.12 迁移作业与自测

迁移作业：把固定行分块改成 Python 函数级分块。可以使用标准库 `ast` 获取行范围，但不要执行被读取的代码。

要求：保留路径与文件版本；处理语法错误文件；大函数超过预算时明确报告而不是静默截断；同一预算下比较必要证据覆盖率。再补一个“保留关键规格片段”的策略，并记录它是否挤掉其他证据。

闭卷回答：

1. 检索没命中与模型没理解，怎样从轨迹区分？
2. 为什么示例的 1100 字符不能叫 1100 Token？
3. 删除工具历史为什么可能破坏下一次 API 请求？
4. 文件哈希相同，是否代表内容正确？
5. 选入更多片段，为什么可能不提高质量？

## 6.13 本轮项目递进与学习账本
